# 후원은 토스페이먼츠 테스트 모드로 받고, 서버가 승인 확인한 주문서만 확정한다

후원 결제는 토스페이먼츠의 **결제창(API 개별 연동) 테스트 키**(`test_ck_`/`test_sk_`)로 한다. 실제 돈은 오가지 않는다. 서버는 `test_`로 시작하지 않는 키로는 켜지지 않는다. 비밀 키는 `.env`에만 두고 서버에서만 쓴다.

흐름은 이렇다. 서버가 먼저 **주문서**(주문 번호, 금액, 방송, 받는 사람, 후원자)를 만들고, 브라우저가 결제창을 띄운다. 돌아온 금액이 주문서와 다르면 거절한다. 같으면 서버가 비밀 키로 토스 승인 API를 부르고, 응답의 상태·금액·주문 번호를 주문서와 다시 맞춘 뒤에만 확정한다. 금액과 받는 사람의 기준은 언제나 서버가 처음 적은 주문서다.

승인 통지(웹훅)는 내용을 믿지 않고, 받을 때마다 토스 조회 API로 다시 확인한다. 돌아온 화면과 승인 통지 중 무엇이 먼저 오든, 몇 번 오든 "결제 대기일 때만 확정으로 바꾼다"는 조건부 전환과 DB의 고유 제약으로 주문서 하나는 한 번만 확정된다.

## Considered Options

- **결제위젯(주문서형) 키**: 토스가 권장하지만, 이 키로는 주문 번호로 결제를 조회하는 API를 부를 수 없고 웹훅 서명용 보안 키도 없다. 승인 통지를 다시 확인하는 데 불편하다.
- **포트원(아임포트)**: 여러 결제사를 묶어 주지만 한 단계가 더 생긴다.
- **Stripe**: 원화·한국어 결제 경험이 약하다.
- **화면의 성공 표시나 통지 내용으로 확정**: 주소를 꾸미거나 통지를 흉내 내면 돈 없이 후원이 쌓인다. 과제도 금지한다.

## 테스트를 위한 장치

- `.env`의 `TOSS_TEST_FAIL_CODE`(예: `REJECT_CARD_PAYMENT`)가 있으면 승인 요청에 토스의 테스트 헤더 `TossPayments-Test-Code`를 붙여 일부러 실패시킨다. 테스트 키일 때만 동작한다. README의 "실패 확인" 절차가 이것을 쓴다.
- 결제 대기 주문서는 30분이 지나면 만료로 바꾼다(토스는 인증 뒤 10분 안에 승인해야 한다). 만료된 주문서로 돌아와도 확정하지 않는다.
- 중복 통지는 같은 모양의 승인 통지를 `curl`로 두 번 보내 확인한다. 진짜 토스 웹훅 수신은 터널 주소를 개발자센터에 등록하는 선택 확인이다.

## 결제 회사와 이야기하는 코드는 "결제 연결" 모듈 하나에 모은다

나중에 배포하거나 다른 결제 회사(포트원, 간편결제사 직접 연동 등)를 붙일 수 있도록, 토스와 주고받는 코드(승인, 조회, 승인 통지 읽기, 테스트 헤더)는 결제 연결 모듈 하나에만 둔다. 주문서, 승인 확인 규칙, 중복 방지, 화면은 "결제 회사가 이 주문 번호·금액으로 승인했다/안 했다"는 결과만 다룬다. 결제 회사를 바꾸거나 더하면 이 모듈만 새로 만든다. 테스트의 가짜 토스 서버도 이 경계 덕분에 쓸 수 있다.

## 승인을 마친 결제는 만료·실패·취소된 주문서도 확정한다

주문서는 원래 결제 대기에서 한 번만 바뀌고 되돌아가지 않는다. 그런데 결제 회사가 승인을 마친(토스 `DONE`) 결제는 돈이 이미 나갔다. 그사이 주문서가 끝났을 수 있다. 승인 요청 도중 만료 정리가 돌았거나, 결제창이 실패를 알렸는데 실제로는 승인됐거나, 승인 뒤 DB 쓰기가 실패하고 승인 통지가 나중에 다시 온 경우다. 이때 주문서를 끝난 채로 두면 돈은 나갔는데 후원은 없다.

그래서 예외를 하나 둔다. 결제 회사에 다시 확인한(승인 응답이나 조회) 결제가 승인 완료이고 주문 번호·금액이 주문서와 같으면, 주문서가 만료·실패·취소였어도 확정으로 바꾼다("늦은 확정", 경고 로그를 남긴다). 이 전환은 "확정이 아닐 때만"을 조건으로 하는 UPDATE 하나이고, 확정된 주문서는 건드리지 않으며 결제 키의 고유 제약도 그대로라 후원은 한 번만 쌓인다. 승인 통지는 주문서가 결제 대기가 아니어도 조회한 결제를 승인 확인에 넘긴다. 반대로 결과 화면의 승인 확인은 끝난 주문서에 승인을 요청하지 않는다(끝난 주문서로 새로 돈이 나가면 안 된다).

같은 이유로, 승인 요청이 오류를 줘도 실패로 단정하지 않는다. 주문 번호로 다시 조회해 결제가 보이면 그 상태로, 조회가 `NOT_FOUND_PAYMENT`면(승인 오류가 다시 해 볼 수 있는 5xx·429·409 처리 중이 아닐 때) 실패로 판단한다. 조회가 닿지 않거나 5xx·429·409이거나 읽지 못하면 "아직 모름"이라 주문서는 결제 대기로 남는다. 승인되지 않은 결제의 실패 이유는 결제 상태(`ABORTED` 등)가 아니라 승인 오류의 코드·메시지(예: `REJECT_CARD_PAYMENT`)를 남긴다.
