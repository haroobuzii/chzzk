# 녹화방송: 치지직 만들기 ④ 후원

방송을 올리고 시청하는 웹 서비스다. 시청은 누구나 하고, 방송을 만들거나 댓글을 쓰거나 후원하려면 로그인한다. 화면과 서버 모두 Rust [Dioxus](https://dioxuslabs.com) 0.7 fullstack 크레이트 하나로 만들었다.

- **1단계 (녹화 방송)**: 제목과 MP4 영상을 올려 방송을 등록하고, 목록에서 골라 상세 화면에서 재생한다.
- **2단계 (라이브 방송)**: 휴대폰 브라우저에서 카메라·마이크로 라이브 방송을 송출하고, 다른 사람은 컴퓨터나 휴대폰 브라우저에서 1초 안팎의 지연으로 시청한다.
- **3단계 (로그인·권한과 댓글)**: 회원가입·로그인이 생겼다. 방송을 만든 사용자가 그 방송의 소유자가 되어 제목 수정, 삭제, 송출과 종료를 소유자만 한다. 로그인한 사용자는 방송에 댓글을 남기고 자기 댓글을 지운다.
- **4단계 (후원)**: 로그인한 사용자가 방송 상세 화면에서 그 방송의 소유자에게 후원한다. 결제는 토스페이먼츠 **테스트 모드**로 하므로 실제 돈은 나가지 않는다. 서버가 토스에 직접 승인 확인을 한 뒤에만 후원이 확정되고, 상세 화면에 후원 합계와 내역이 보인다.

"치지직 만들기" 과제의 마지막(4단계) 단계이며, 1~3단계 기능을 그대로 유지하며 확장했다. 화면에 보이는 서비스 이름은 "녹화방송"이고, 실제 치지직의 로고·이름·색은 쓰지 않는다.

용어(방송, 녹화 방송, 라이브 방송, 방송 상태, 송출, 시청, 방송 번호, 사용자, 로그인, 소유자, 댓글, 작성자, 후원, 후원자, 주문서, 승인 확인, 승인 통지)는 [GLOSSARY.md](GLOSSARY.md)를 따른다. 과제 이름의 "도네이션"을 이 문서와 화면에서는 "후원"이라고 부른다. 2단계의 "송출 키"는 3단계에서 소유자 확인으로 바뀌어 없어졌다.

## 4단계 구현 범위

> **테스트 결제다. 실제로 돈이 나가지 않는다.** 서버는 토스페이먼츠의 테스트 키(`test_`로 시작)로만 켜진다. 라이브 키(`live_`)를 넣으면 이유를 알려 주고 켜지지 않는다. 테스트 모드에서는 결제창에 진짜 카드 정보를 넣어 결제가 승인되어도 카드에서 돈이 빠져나가지 않는다. 후원 칸과 결과 화면에도 언제나 "테스트 결제 · 실제로 돈이 나가지 않아요"가 보인다.

| 기능 | 내용 |
|---|---|
| 후원 칸 | 녹화 방송과 라이브 방송의 상세 화면에 "후원" 칸이 있다. 합계("총 35,000원 · 7건")와 내역(후원자 아이디, 금액, 메시지, 시각)이 최신순으로 보인다. 확정된 후원만 보이고, 결제 대기·실패·취소·만료된 주문서는 보이지 않는다. 비로그인도 볼 수 있다. |
| 후원하기 | 다른 사람의 방송에서 1,000원·5,000원·10,000원·50,000원 버튼으로 고르거나 직접 입력하고(1,000~500,000원, 100원 단위), 응원 메시지(100자까지, 쓰지 않아도 됨)를 적어 "후원하기"를 누른다. 규칙에 맞지 않으면 결제창이 열리기 전에 이유가 나온다. |
| 결제창 | 토스페이먼츠 카드 결제창이 열린다. 결제창에 받는 방송자와 금액이 보인다. 그 창 안에서 카드나 간편결제를 고른다. |
| 결과 화면 | 결제를 마치면 `/donations/success`에서 "후원이 완료되었습니다"와 금액·방송이, 실패하면 `/donations/fail`에서 이유가 나온다. 결제창을 닫으면 "결제를 취소했습니다"가 나온다. 둘 다 방송으로 돌아가는 링크가 있다. 새로고침하거나 뒤로 갔다 와도 후원은 한 번만 쌓인다. |
| 후원할 수 없는 곳 | 로그인 전에는 "로그인하고 후원하기"가 보인다(누르면 로그인 뒤 이 방송으로 돌아온다). 내 방송과 소유자 없는 1·2단계 방송에는 후원 입력이 없고, 요청을 직접 보내도 서버가 400으로 거절한다. |
| 라이브 방송 중 갱신 | 방송 중인 라이브 방송에서는 후원 합계와 내역이 5초마다 저절로 새로 고쳐진다. |
| 만료 | 결제창을 연 채 30분이 지난 주문서는 서버가 1분마다 만료로 정리한다. 그 뒤에 돌아오면 "시간이 지나 결제가 취소되었어요"가 나온다. 단 토스가 승인을 마친 결제는 돈이 이미 나갔으므로, 만료·실패·취소된 주문서라도 승인 통지로 확인되면 확정된다. |
| 토스 키가 없을 때 | `.env`에 토스 키가 없어도 서버는 켜지고 1~3단계 기능은 그대로다. 후원 칸에는 "후원 기능을 쓰려면 토스 테스트 키가 필요해요"가 보인다. |
| 서버 재시작 | 주문서와 확정된 후원은 DB에 있어 서버를 다시 켜도 그대로다. 방송을 지워도 그 방송의 주문서는 돈과 관련된 기록이라 지우지 않고 남긴다(지운 방송의 후원은 어디에도 보이지 않는다). |

### 후원 흐름과 승인 확인

설계 배경은 [ADR 0007](docs/adr/0007-donations-via-toss-test-mode.md)에 있다. 핵심은 "화면이나 통지가 성공이라고 해도 믿지 않고, 서버가 토스에 직접 확인한 주문서만 확정한다"이다.

```
후원자 브라우저                 우리 서버                                  토스페이먼츠 (테스트 모드)
 "후원하기" ── 금액·메시지 ──► ① 주문서를 만든다
                               (주문 번호, 금액, 방송, 받는 사람=소유자, 후원자, 상태=결제 대기)
            ◄── 주문 번호·금액·클라이언트 키
 ② 결제창을 연다 ─────────────────────────────────────────────────────► 카드 정보 입력, 인증
            ◄──────────────────── /donations/success?paymentKey&orderId&amount ──┘
 ③ 결과 화면이 돌아온 값을 보냄 ► 승인 확인
                               1. 주문서가 결제 대기인가 (이미 확정이면 그 결과를 그대로 준다)
                               2. 30분이 지났으면 만료
                               3. 돌아온 금액 = 주문서 금액인가 (다르면 토스를 부르지 않고 실패)
                               4. 비밀 키로 승인 API 호출 ─────────────► POST /v1/payments/confirm
                               5. 응답의 상태 DONE, 금액, 주문 번호가 ◄── 결제 정보
                                  주문서와 같을 때만 ④ 확정
                                                                  ◄── 승인 통지(웹훅): 결제 키만 읽고
                                                                       GET /v1/payments/{결제 키}로 다시 조회해
                                                                       같은 승인 확인에 넘긴다
```

- **금액과 받는 사람은 서버가 정한다.** 기준은 언제나 서버가 처음 적은 주문서다. 돌아온 주소의 `amount`를 바꾸면 3번에서 실패(`amount_mismatch`)가 되고 토스에는 승인을 요청하지도 않는다.
- **비밀 키는 서버에만 있다.** 브라우저에는 원래 공개해도 되는 클라이언트 키만 간다. 승인 API는 비밀 키로 Basic 인증을 하고, `Idempotency-Key`로 주문 번호를 붙여 같은 승인을 두 번 요청해도 토스가 첫 결과를 다시 준다.
- **승인 요청이 오류여도 바로 실패로 보지 않는다.** "이미 처리된 결제" 같은 오류일 수 있으므로 주문 번호로 토스에 다시 조회해 실제 상태로 판단한다. 토스에 닿지 않으면 주문서를 결제 대기로 두고 "잠시 뒤 새로고침해 주세요"를 보여 준다.
- **한 번만 확정된다.** 주문서 상태는 "결제 대기일 때만 바꾼다"는 조건이 붙은 UPDATE 한 번으로 바꾼다. 결과 화면 새로고침, 같은 승인 통지 여러 번, 결과 화면과 승인 통지가 동시에 와도 이기는 것은 하나뿐이다. DB에도 주문 번호와 결제 키(`payment_key`)에 고유 제약이 있어 "결제 한 건 = 후원 한 건"을 한 번 더 막는다.
- **승인 통지는 내용을 믿지 않는다.** 누구나 그럴듯한 통지를 꾸며 보낼 수 있으므로 본문에서는 결제 키만 읽고, 비밀 키로 토스에 다시 조회한 결과로만 판단한다. 그래서 웹훅 서명 검증은 하지 않는다. 토스가 10초 안에 200을 받지 못하면 다시 보내므로, 모르는 결제나 틀린 본문에도 언제나 빨리 200을 준다.
- **결제 회사와 이야기하는 코드는 한 곳에 있다.** 토스와 주고받는 코드(승인, 조회, 테스트 헤더)는 `src/donations/toss/`에만 있고, 나머지는 "이 주문 번호·금액으로 승인됐다/안 됐다/아직 모른다"는 결과만 다룬다. 자동 테스트는 이 경계에 가짜 토스 서버를 끼운다.

### 4단계 범위 밖과 한계

- **실제 결제를 하지 않는다.** 라이브 키, 사업자 등록·전자결제 계약, 실제 서버 배포는 하지 않는다.
- 환불(결제 취소 API), 부분 취소. 테스트 결제는 토스 개발자센터의 테스트 결제내역에서 취소할 수 있지만, 그래도 우리 서비스의 후원은 그대로 남는다.
- 정산, 방송자 수익 화면, 출금
- 카드 결제창 밖의 결제 수단(계좌이체, 휴대폰, 가상계좌) 버튼. 계좌이체는 테스트에도 공동인증서가 필요하고, 가상계좌는 입금 대기 상태가 따로 생긴다. 결제 회사와 이야기하는 코드를 한 곳에 모아 두어 나중에 더할 수 있다.
- 토스 결제위젯(주문서형). 전자결제 계약 뒤에 받는 키가 필요하고, 주문 번호로 결제를 조회할 수 없다([ADR 0007](docs/adr/0007-donations-via-toss-test-mode.md)).
- 웹훅 서명 검증. 통지 내용을 쓰지 않고 토스에 다시 조회하므로 필요 없다.
- 후원 순위, 후원 알림 팝업·음성, 후원 목표, 후원 메시지 지우기
- 토스 테스트 환경은 API마다 분당 100건으로 제한된다. 자동 테스트는 가짜 토스 서버를 쓰므로 영향이 없다.

## 3단계 구현 범위

| 기능 | 내용 |
|---|---|
| 회원가입 (`/signup`) | 아이디와 비밀번호로 가입한다. 아이디는 2~20자의 한글·영문·숫자·밑줄이고, 영문 대소문자만 다른 아이디(`Haroo`와 `haroo`)는 같은 아이디로 본다. 비밀번호는 8~128자다(아주 긴 비밀번호로 해시 계산에 서버가 묶이지 않게 최대를 둔다). 어기면 한국어 이유가 나오고, 이미 쓰는 아이디면 "이미 쓰는 아이디예요"가 나온다. 가입이 끝나면 바로 로그인된다. |
| 로그인 (`/login`) | 아이디와 비밀번호로 로그인한다. 실패하면 아이디가 없든 비밀번호가 틀리든 같은 문구 "아이디 또는 비밀번호가 맞지 않아요"가 나온다. 로그인은 7일 동안 유지된다. |
| 머리글 | 로그인 전에는 "로그인" 버튼, 로그인 뒤에는 "아이디님"과 "로그아웃" 버튼이 보인다. "라이브 시작"과 "녹화 올리기"는 그대로 있다. |
| 로그인 뒤 돌아가기 | 로그인이 필요한 화면(`/new`, `/live/new`)에 로그인 없이 들어가면 `/login?next=<원래 주소>`로 보내지고, 로그인하면 원래 화면으로 돌아간다. `next`는 이 서비스 안의 주소(`/`로 시작하고 `//`로 시작하지 않음)만 받고, 아니면 첫 화면으로 간다. |
| 소유자 | 녹화 방송을 등록하거나 라이브 방송을 시작한 사용자가 그 방송의 소유자다. 목록 카드와 상세 화면에 소유자 아이디가 보인다. 1·2단계에서 만든 방송은 "익명"(소유자 없음)이다. |
| 제목 수정 | 소유자의 상세 화면에만 "제목 수정"이 보인다. 그 자리에서 고치고 "저장"한다. 규칙은 등록 때와 같다(1~100자). 라이브 방송 중에도 고칠 수 있고, 시청 화면과 목록에 5초 안에 반영된다. |
| 삭제 | 소유자의 상세 화면에만 "삭제"가 보인다. "정말 삭제할까요?" 확인 뒤 방송 정보, 영상 파일, 그 방송의 댓글을 모두 지운다. 방송 중인 라이브 방송이면 송출을 끊은 뒤 지운다. 지운 방송의 주소는 "방송을 찾을 수 없습니다"(404)가 되고, 보고 있던 시청자에게도 몇 초 안에 그렇게 나온다. |
| 송출과 종료 | 송출 연결과 종료는 로그인한 소유자만 할 수 있다(2단계의 송출 키를 대신함). 송출 화면을 닫아 버렸어도 소유자는 상세 화면의 "방송 종료"로 방송을 끝낼 수 있다. |
| 댓글 | 녹화 방송과 라이브 방송 상세 화면 아래에 댓글 칸이 있다. 댓글은 누구나 읽고, 오래된 순으로 작성자 아이디와 쓴 시각(한국 시간)이 보인다. 로그인한 사용자만 1~300자 댓글을 쓴다(앞뒤 공백은 지움). 내 댓글에만 "삭제"가 붙는다. 수정은 없다. 로그인하지 않았으면 입력 칸 대신 "로그인하고 댓글을 남겨 보세요"와 로그인 링크가 보인다. |
| 댓글 갱신 | 방송 중인 라이브 방송에서는 댓글이 3초마다 저절로 새로 고쳐진다. 종료된 라이브 방송에도 댓글을 남길 수 있다. |
| 서버에서 권한 검사 | 화면에서 버튼을 숨기는 것과 별개로, 모든 권한 검사는 서버가 요청마다 한다. 화면을 거치지 않고 요청을 직접 보내도 비로그인은 401, 권한 없는 사용자는 403으로 거절되고 방송·댓글은 그대로다. 아래 "화면을 거치지 않는 요청으로 확인"에 `curl` 예시가 있다. |
| 서버 재시작 | 사용자, 로그인, 방송 소유, 댓글은 DB에 있어 서버를 다시 켜도 그대로다. |

### 공개 범위 (4단계 후원 포함)

| 할 수 있는 일 | 비로그인 | 로그인한 사용자 | 방송 소유자 | 댓글 작성자 |
|---|---|---|---|---|
| 방송 목록 보기, 녹화 방송 재생, 라이브 방송 시청 | O | O | O | O |
| 댓글 읽기 | O | O | O | O |
| 녹화 방송 등록, 라이브 방송 시작 | X (401) | O | O | O |
| 댓글 쓰기 | X (401) | O | O | O |
| 방송 제목 수정, 방송 삭제 | X (401) | X (403) | O (자기 방송만) | - |
| 라이브 방송 송출 연결, 방송 종료 | X (401) | X (403) | O (자기 방송만) | - |
| 댓글 삭제 | X (401) | X (403) | X (403, 남의 댓글은 소유자도 못 지움) | O (자기 댓글만) |
| 후원 합계·내역 보기 (4단계) | O | O | O | O |
| 후원하기 (4단계) | X (401) | O (소유자가 있는 남의 방송) | X (400, 자기 방송에는 못 함) | - |
| 결제 실패·취소 보고 (4단계, 결과 화면이 부름) | X (401) | O (자기 주문서만 바뀜) | - | - |

- 괄호 안 숫자는 화면을 거치지 않고 요청을 보냈을 때 서버가 돌려주는 상태 코드다. 401은 "로그인이 필요해요"(`login_required`), 403은 "권한이 없어요"(`forbidden`)다.
- 소유자가 없는 1·2단계 방송("익명")은 누구도 수정·삭제할 수 없다(로그인했으면 403). 후원도 받을 수 없다(400, `no_owner`).
- 결제 뒤의 승인 확인(`/api/donations/confirm`)은 로그인을 요구하지 않는다. 결제창에 다녀오는 사이 로그인이 끊겨도 이미 한 결제는 확정되어야 하기 때문이다. 대신 서버가 주문서와 토스에 직접 확인하므로, 남이 부르거나 값을 바꿔 불러도 후원이 새로 생기거나 금액이 바뀌지 않는다.
- 화면도 같은 규칙을 따른다. 남의 방송 상세 화면에는 "제목 수정"·"삭제"·"방송 종료" 버튼이 없고, 남의 댓글에는 "삭제"가 없다.

### 로그인 방식

로그인은 서버 세션과 쿠키로 유지한다([ADR 0006](docs/adr/0006-server-sessions-in-cookies.md)).

- 로그인하면 서버가 긴 무작위 세션 값을 만들어 `chzzk_session` 쿠키로 준다. DB에는 그 값의 해시와 사용자, 만료 시각만 저장한다.
- 쿠키에는 `HttpOnly`(자바스크립트가 읽지 못함), `SameSite=Lax`(다른 사이트에서 보낸 POST에 실리지 않음), `Path=/`, `Max-Age=604800`(7일)이 붙는다. HTTPS(터널 주소)로 들어왔으면 `Secure`도 붙는다.
- 로그아웃하면 DB의 세션을 지우므로, 그 쿠키는 그 즉시 무효가 된다. 7일이 지난 세션도 로그인으로 치지 않는다.
- 비밀번호는 원문을 저장하지 않고 Argon2 해시로만 저장한다.
- 상태를 바꾸는 요청(POST·PATCH·DELETE)은 다른 사이트에서 온 것이면 403으로 거절한다(CSRF 막기). 브라우저가 붙이는 `Sec-Fetch-Site`가 있으면 `same-origin`일 때만 받고, 없으면 `Origin`을 요청 주소와 비교한다. 둘 다 없는 요청(`curl`, 테스트)은 쿠키 규칙만 따른다.
- 휴대폰(터널의 `https://…trycloudflare.com` 주소)과 컴퓨터(`http://localhost:8080`)는 주소가 달라 쿠키가 따로 생긴다. 같은 사람이 두 곳에서 쓰려면 각각 로그인해야 한다.

### 3단계 범위 밖과 한계

- **로그인 시도 횟수 제한이 없다.** 같은 아이디로 비밀번호를 계속 바꿔 넣어 보는 공격(무차별 대입)을 막지 않는다. 실제 서비스라면 시도 횟수 제한이나 지연을 더해야 한다.
- 이메일, 이메일 인증, 비밀번호 찾기·바꾸기, 회원 탈퇴, 프로필(사진·소개)
- 소셜 로그인, 2단계 인증
- 댓글 수정, 답글, 좋아요, 신고, 방송 소유자가 남의 댓글을 지우는 관리 기능
- 관리자 역할, 방송 공개·비공개 설정, "내 방송" 모아 보기 화면
- 녹화 방송의 영상 바꾸기(수정은 제목만), 라이브 다시 보기
- 실시간 알림 장치(WebSocket). 댓글과 방송 상태는 주기적으로 다시 묻는다.
- 실제 서버 배포. 후원(과제의 도네이션)은 4단계에서 구현했다.

## 2단계 구현 범위 (3단계에서 일부 바뀜)

3단계부터 라이브 방송을 시작하려면 로그인해야 하고, 송출 키 대신 로그인한 소유자인지로 송출과 종료를 지킨다. 나머지 동작은 그대로다.

| 기능 | 내용 |
|---|---|
| 머리글 | "라이브 시작"(`/live/new`)과 "녹화 올리기"(`/new`) 두 버튼. 휴대폰 폭에서도 한 줄에 놓인다. |
| 송출 화면 (`/live/new`) | 제목을 넣고, 카메라 미리보기(기본 후면 카메라, 미리보기 소리는 꺼 둠)를 본 뒤 "방송 시작"을 누른다. 연결 중에는 "연결하는 중…"이 보이고 버튼이 잠긴다. 송출이 시작되면 빨간 LIVE 표시와 시청 주소(복사 버튼)가 나온다. |
| 카메라 전환 | 방송 전과 방송 중 모두 전면·후면 카메라를 바꿀 수 있다. 방송 중에는 연결을 끊지 않고 보내는 영상만 바꿔 끼운다. |
| 송출 종료 | "방송 종료"를 누르면 송출이 멈추고, 방송 상태가 종료가 되고, 카메라와 마이크가 꺼진다. |
| 자동 종료 | 송출 화면을 닫거나, 와이파이가 끊기거나, 화면이 잠겨 영상이 끊기면 서버가 몇 초 안에 알아채 방송을 종료로 바꾼다. 송출 화면을 떠날 때도 종료 요청을 한 번 보낸다. |
| 화면 꺼짐 막기 | 송출 중에는 화면이 저절로 꺼지지 않게 한다(Screen Wake Lock). 지원하지 않는 브라우저에서는 "송출 중에는 화면을 켜 두세요"를 보여 준다. |
| 안내 문구 | 카메라·마이크 권한 거절, HTTPS가 아닌 주소, 카메라 없음·사용 중, 송출 연결 실패(같은 와이파이인지 확인하라는 안내 포함)를 각각 한국어로 알려 준다. |
| 송출·종료 보호 | 다른 사람이 내 방송을 끄거나 다른 영상을 끼워 보내지 못하게 한다. 2단계에서는 시작한 화면만 받는 송출 키로 지켰고, 3단계에서는 송출 키를 없애고 로그인한 소유자만 송출 연결과 종료를 하게 바꿨다([ADR 0005](docs/adr/0005-stream-key-instead-of-login.md)). |
| 방송 상태 | 준비 → 방송 중 → 종료 순서로만 바뀌고 되돌아가지 않는다. 시작했지만 30초 안에 영상이 들어오지 않은 방송은 버려지며 화면 어디에도 보이지 않는다. |
| 목록 (`/`) | 방송 중인 방송이 있으면 맨 위에 "지금 라이브" 칸이 나온다. 그 아래 녹화·라이브 방송이 함께 최신순으로 나온다. 카드마다 녹화 / 빨간 LIVE / 종료 표시가 붙는다. 5초마다 저절로 갱신된다. |
| 시청 (`/broadcasts/번호`) | 녹화 방송과 같은 주소 모양이다. 방송 중이면 실시간 영상이 소리 꺼진 채 자동 재생되고, "소리 켜기" 버튼으로 소리를 켠다. 방송이 끝나면 몇 초 안에 "방송이 종료되었습니다"가 나온다. |
| 종료된 라이브 방송 | 제목, 시작 시각, 방송한 시간(예: 12분 34초)을 보여 준다. 다시 볼 수는 없다. 준비 중이거나 버려진 방송 주소는 "방송을 찾을 수 없습니다"(404)다. |
| 서버 재시작 | 라이브 방송 기록(제목, 상태, 시작·종료 시각)은 DB에 남는다. 서버가 꺼진 동안 끝난 방송은 서버가 켜질 때 바로 종료로 바뀐다. |

### 2단계 범위 밖

- 로그인·인가, 방송 소유자(3단계에서 구현). 2단계의 송출 키는 로그인이 아니라 방송 하나에만 쓰는 열쇠였다.
- 댓글(3단계에서 구현), 후원(4단계에서 구현)
- 라이브 다시 보기(녹화 저장), 썸네일, 시청자 수, 채팅
- LTE·5G 등 컴퓨터와 다른 네트워크에서의 송출, TURN 서버. 휴대폰과 컴퓨터는 같은 와이파이에 있어야 한다([ADR 0004](docs/adr/0004-live-via-mediamtx-webrtc.md)).
- 화질 선택, 송출 중 제목 바꾸기, 방송 수정·삭제([ADR 0002](docs/adr/0002-no-edit-or-delete-without-auth.md)). 제목 수정(방송 중에도)과 삭제는 3단계에서 소유자에게 열었다.
- 실제 서버 배포. 내 컴퓨터와 Cloudflare 무료 터널까지만 한다.
- 실시간 알림 장치(WebSocket 등). 목록과 시청 화면은 5초마다 서버에 다시 묻는다.

## 1단계 구현 범위 (그대로 유지)

| 기능 | 내용 |
|---|---|
| 방송 등록 | `/new`에서 제목과 MP4 파일을 골라 등록한다. 업로드 진행률(%)이 보이고, 업로드 중에는 버튼이 잠긴다. 등록이 끝나면 새 방송의 상세 화면으로 간다. |
| 등록 규칙 | 제목은 앞뒤 공백을 지운 뒤 1~100자(문자 수)이고, 같은 제목도 된다. 파일은 확장자 `.mp4`와 파일 앞부분의 `ftyp` 표시로 MP4인지 본다. 최대 크기는 2 GiB(설정 가능)다. 어기면 한국어 이유를 보여 준다. |
| 원자적 등록 | 업로드가 끝까지 성공해야만 방송이 생긴다. 거절되거나 중간에 끊긴 등록은 방송 정보도, 영상 파일도 남기지 않는다. |
| 방송 목록 (`/`) | 최신 등록순 카드 격자. 카드에는 썸네일 자리(회색 칸), 제목, 등록 시각(한국 시간)이 있다. 방송이 없으면 "아직 방송이 없습니다"와 등록 버튼을 보여 준다. |
| 상세 화면 (`/broadcasts/번호`) | 영상 재생기, 제목, 등록 시각, 목록으로 돌아가는 링크. 영상은 원본 그대로 Range 요청으로 받으므로 끝까지 내려받지 않고 건너뛸 수 있다. |
| 없는 방송 | 없는 번호, `0`, `01`, `abc` 같은 주소나 정해지지 않은 주소는 404와 "방송을 찾을 수 없습니다"를 보여 준다. |
| 영속 저장 | 방송 정보는 PostgreSQL에, 영상은 보관 폴더(`DATA_DIR`)에 저장한다. 서버를 다시 켜도 그대로 조회된다. |
| 로그인 | 1단계에서는 로그인 없이 썼다. 3단계부터 조회는 그대로 누구나 하고, 등록은 로그인한 사용자만 한다(로그인 없이 보내면 401). |

라이브 방송의 제목 규칙도 녹화 방송과 같다. 1단계에서 저장한 방송은 2단계로 바꾼 뒤 녹화 방송으로 그대로 조회된다.

### 1단계 범위 밖

- 인증·인가, 방송 소유자, 방송 수정·삭제 (3단계에서 구현). 인증이 없는데 수정·삭제를 열면 누구나 남의 방송을 바꿀 수 있어서 만들지 않았다([ADR 0002](docs/adr/0002-no-edit-or-delete-without-auth.md)).
- 라이브 송출 (2단계에서 구현), 댓글 (3단계에서 구현), 후원 (4단계에서 구현)
- 영상 변환(HLS 등)·화질 선택·코덱 검사([ADR 0001](docs/adr/0001-serve-original-mp4.md)), 썸네일 생성, 재생 시간 표시
- 목록 페이지네이션·검색, 업로드 이어 올리기, 도배 방지
- 실제 서버 배포와 HTTPS. 1단계는 내 컴퓨터에서 실행한다.

## 구성

### 1단계: 녹화 방송

```
브라우저 ──► Dioxus fullstack 서버 (Rust, 크레이트 하나)
              ├─ 화면: 목록 / 상세 / 등록 (서버에서 그린 뒤 WASM이 이어받음)
              ├─ 서버 함수: GET /api/broadcasts/list, GET /api/broadcasts/info?id=번호
              ├─ axum 라우트: POST /api/broadcasts (multipart 등록)
              │               GET  /api/broadcasts/{번호}/video (Range 지원 영상 전송)
              ├─► PostgreSQL: broadcasts 표 (방송 번호, 제목, 영상 키, 등록 시각)
              └─► 보관 폴더(DATA_DIR): videos/<번호>.mp4
```

### 2단계: 라이브 방송

휴대폰은 WebRTC로 미디어 서버 [MediaMTX](https://github.com/bluenviron/mediamtx)에 영상을 보내고(WHIP), 시청자는 MediaMTX에서 받는다(WHEP). 우리 서버는 라이브 방송의 정보, 방송 상태, 송출 권한(3단계부터 소유자 확인)만 관리하고 영상은 다루지 않는다([ADR 0004](docs/adr/0004-live-via-mediamtx-webrtc.md)).

```
                         ┌──────────────────────── 내 컴퓨터 ─────────────────────────┐
 휴대폰 (송출)            │                                                             │
  화면·연결 요청 ─HTTPS─► Cloudflare 터널 ─► 우리 서버 (localhost:8080)                │
                         │                    ├─ 소유자 확인 뒤 WHIP/WHEP 요청을 넘김 ─┐ │
 컴퓨터 브라우저 (시청)   │                    ├─ 상태 감시기: 2초마다 경로 목록 확인 ──┤ │
  http://localhost:8080 ─────────────────────►├─► PostgreSQL (localhost:5433)         │ │
                         │                    │                                      ▼ │
                         │                    │          MediaMTX (Docker)              │
                         │                    │           ├─ WHIP/WHEP: 127.0.0.1:8889 │
                         │                    │           ├─ 관리 API:  127.0.0.1:9997 │
  휴대폰 영상 ─────────── 같은 와이파이, UDP ─────────────►└─ 영상:     LAN_IP:8189/udp │
                         └────────────────────────────────────────────────────────────┘
```

- **터널**: 휴대폰 브라우저는 HTTPS 주소에서만 카메라를 쓰게 해 준다. 그래서 `cloudflared`로 `https://…trycloudflare.com` 주소를 만든다. 터널은 화면과 연결 요청만 나른다.
- **같은 와이파이**: 영상 자체는 터널을 지나지 않고, 휴대폰이 같은 와이파이 안의 컴퓨터(`LAN_IP`의 UDP 8189번)로 직접 보낸다. 그래서 휴대폰과 컴퓨터가 같은 와이파이에 있어야 한다. 손님용 와이파이처럼 기기끼리 막아 둔 망에서는 송출이 연결되지 않는다.
- **보안 경계**: MediaMTX의 HTTP 포트(8889, 9997)는 내 컴퓨터 안(127.0.0.1)에만 열린다. 휴대폰과 시청자는 반드시 우리 서버를 거쳐야 MediaMTX에 닿으므로, 송출 권한 확인(3단계부터 소유자 확인)을 건너뛸 수 없다.
- **상태 감시기**: 서버가 켜지면 2초마다 MediaMTX의 "지금 영상이 들어오는 경로"(`live/<방송 번호>`) 목록과 DB를 맞춘다. 영상이 들어오면 방송 중, 사라지면 종료, 준비로 30초가 지나면 버려짐이 된다.

라이브 방송에 쓰는 HTTP 라우트는 아래와 같다(3단계 기준). 실패 응답은 1단계와 같은 `{code, message}` JSON이다.

| 요청 | 하는 일 |
|---|---|
| `POST /api/live` | 로그인 필요. 제목(JSON `{title}`)을 받아 준비 상태의 라이브 방송을 만들고 201과 `{id}`(방송 번호)를 준다. 요청한 사용자가 소유자가 된다. 비로그인은 401. |
| `POST /api/live/{번호}/whip` (+ `/whip/{세션}`의 `PATCH`·`DELETE`) | 송출 연결. 로그인한 소유자일 때만 MediaMTX에 넘긴다. 비로그인 401, 다른 사용자 403. 준비가 아닌 방송은 409. |
| `POST /api/live/{번호}/whep` (+ 세션 `PATCH`·`DELETE`) | 시청 연결. 누구나 쓰며, 방송 중일 때만 넘긴다. |
| `POST /api/live/{번호}/end` | 소유자면 204와 함께 종료한다. 이미 종료된 방송도 204다. 비로그인 401, 다른 사용자 403. |

2단계에서는 `POST /api/live`가 `{id, key}`를 주고, 송출 연결과 종료에 `Authorization: Bearer <송출 키>`를 썼다. 3단계에서 송출 키를 없앴다.

### 3단계: 로그인·권한과 댓글

```
브라우저 ──(쿠키 chzzk_session)──► 우리 서버
                                  ├─ 현재 사용자 확인: 쿠키 → DB의 세션 → 비로그인 / 사용자
                                  ├─ 다른 사이트에서 온 상태 변경 요청 거절(CSRF)
                                  ├─ 권한 검사: 로그인 필요(401) / 권한 없음(403) / 소유자·작성자 확인
                                  └─► PostgreSQL: users, sessions, broadcasts(+소유자), comments
```

모든 권한 검사는 "현재 사용자 확인" 한 곳을 거친다. 화면은 같은 규칙으로 버튼을 보이거나 숨길 뿐이고, 허용·거절은 서버가 정한다.

| 요청 | 하는 일 |
|---|---|
| `POST /api/auth/signup` `{username, password}` | 가입. 201과 세션 쿠키, `{username}`. 규칙 위반 400, 이미 쓰는 아이디 409. |
| `POST /api/auth/login` `{username, password}` | 로그인. 200과 세션 쿠키. 실패는 401(`bad_credentials`). |
| `POST /api/auth/logout` | 204. 세션을 지우고 쿠키를 만료시킨다. 로그인하지 않았어도 204. |
| `GET /api/auth/me` | 200과 `{username}`, 로그인하지 않았으면 `{username: null}`. |
| `POST /api/broadcasts` | 녹화 방송 등록(1단계와 같음). 로그인 필요, 비로그인 401. |
| `PATCH /api/broadcasts/{번호}` `{title}` | 제목 수정. 소유자면 200. 비로그인 401, 다른 사용자·소유자 없는 방송 403, 제목 위반 400, 없는 방송 404. |
| `DELETE /api/broadcasts/{번호}` | 삭제. 소유자면 204. 권한 규칙은 제목 수정과 같다. |
| `GET /api/broadcasts/{번호}/comments` | 댓글 목록. 누구나. 오래된 순 `[{id, author, body, created_at, mine}]`. `mine`은 내가 쓴 댓글인지다. |
| `POST /api/broadcasts/{번호}/comments` `{body}` | 댓글 쓰기. 로그인 필요(401). 201과 그 댓글. 본문 위반 400, 없는 방송 404. |
| `DELETE /api/comments/{댓글 번호}` | 댓글 삭제. 작성자면 204, 다른 사용자 403, 비로그인 401, 없는 댓글 404. |

목록·상세 조회 결과에는 소유자 아이디(`owner`, 소유자 없으면 비어 있음)가 더해졌다.

### 4단계: 후원

```
후원자 브라우저 ──► 우리 서버 ─────────────────────────────► 토스페이먼츠 API (테스트 키)
  │  후원 칸, 결과 화면   ├─ 주문서 만들기, 승인 확인, 실패·취소 보고     승인 POST /v1/payments/confirm
  │                     ├─ 승인 통지 받기 ◄─────────────────────── 웹훅 (선택: 터널 주소를 등록했을 때)
  │                     ├─ 만료 정리: 1분마다 30분 지난 결제 대기 → 만료  조회 GET /v1/payments/{결제 키}
  │                     └─► PostgreSQL: donation_orders(주문서)           GET /v1/payments/orders/{주문 번호}
  └──► 토스 결제창 (js.tosspayments.com의 v2 SDK, 클라이언트 키만 씀)
```

후원에 쓰는 HTTP 라우트는 아래와 같다. 실패 응답은 1~3단계와 같은 `{code, message}` JSON이고, 401·403 규칙도 3단계와 같다.

| 요청 | 하는 일 |
|---|---|
| `GET /api/broadcasts/{번호}/donations` | 후원 합계와 내역. 누구나. `{total_amount, count, items: [{donor, amount, message, confirmed_at}], enabled}`. 확정된 후원만 최신순이다. `enabled`는 서버에 토스 키가 있어 후원할 수 있는지다. 없는 방송 404. |
| `POST /api/broadcasts/{번호}/donations` `{amount, message?}` | 주문서 만들기. 로그인 필요(401). 201과 `{order_id, amount, order_name, client_key}`. 소유자 없는 방송 400(`no_owner`), 내 방송 400(`own_broadcast`), 금액·메시지 위반 400, 없는 방송 404, 토스 키 없음 503(`donations_disabled`). |
| `POST /api/donations/confirm` `{payment_key, order_id, amount}` | 승인 확인. 결과 화면 `/donations/success`가 부른다. 로그인은 요구하지 않는다. 200과 `{status, broadcast_id, amount, code?, message?}`. `status`는 `confirmed`(확정)·`failed`(실패)·`canceled`(취소)·`expired`(만료)이고, 같은 요청을 다시 보내도 같은 결과다. 없는 주문서 404, 토스 결과를 아직 알 수 없으면 502(`payment_unknown`, 주문서는 결제 대기로 남는다). |
| `POST /api/donations/fail` `{order_id?, code, message?}` | 실패·취소 보고. 결과 화면 `/donations/fail`이 부른다. 로그인 필요(401). 로그인한 후원자 본인의 결제 대기 주문서만 바꾼다. 토스 취소 코드(`PAY_PROCESS_CANCELED`, `USER_CANCEL`)면 취소, 그 밖은 실패다. 주문 번호가 없거나 남의 주문서면 아무것도 바꾸지 않고 204. |
| `POST /api/payments/toss-webhook` | 승인 통지(토스가 부른다). 본문에서 결제 키만 읽고 토스에 다시 조회해 승인 확인에 넘긴다. 조회한 상태가 `DONE`이고 금액·주문 번호가 맞으면 확정, `CANCELED`·`ABORTED`·`EXPIRED`면 결제 대기 주문서를 취소·실패·만료로 바꾼다. 결과와 상관없이 언제나 200. 쿠키도 `Origin`도 없는 서버 간 요청이라 다른 사이트 요청 막기(CSRF)에 걸리지 않는다. |

화면 주소는 결과 화면 두 개가 더해졌다. 결제창이 돌려보내는 `/donations/success?paymentKey=…&orderId=…&amount=…`와 `/donations/fail?code=…&message=…&orderId=…`다. 화면은 주소의 값을 서버에 넘길 뿐이고, 보여 주는 결과는 서버 응답만 따른다.

## 실행 방법

필요한 것: Rust(rustup. 버전은 `rust-toolchain.toml`에 고정되어 있어 처음 빌드할 때 자동으로 설치된다), [Dioxus CLI](https://dioxuslabs.com/learn/0.7/getting_started) 0.7, Docker, 라이브 송출을 해 볼 때는 `cloudflared`와 휴대폰

1. 환경 변수 파일을 만든다. 들어 있는 값은 로컬 개발용 예시다.

   ```bash
   cp .env.example .env
   ```

2. `.env`의 `LAN_IP`를 이 컴퓨터의 와이파이 IP로 바꾼다. 휴대폰이 영상을 보낼 주소다.

   ```bash
   # macOS
   ipconfig getifaddr en0
   ```

   - 위 명령이 아무것도 출력하지 않으면 `en1`로 해 본다. 시스템 설정 → Wi-Fi → 연결된 와이파이의 "세부사항"에서도 볼 수 있다.
   - Linux는 `hostname -I`, Windows는 `ipconfig`의 "IPv4 주소"를 본다.
   - 보통 `192.168.x.x`나 `10.x.x.x` 모양이다. 와이파이를 바꾸면 IP도 바뀔 수 있으니, 그때는 `.env`를 고치고 2번 단계를 다시 한다.

3. Docker로 PostgreSQL과 MediaMTX를 띄운다. 다른 프로젝트와 겹치지 않게 PostgreSQL은 호스트의 5433번 포트를 쓴다. `LAN_IP`가 비어 있으면 이 명령이 오류로 알려 준다.

   ```bash
   docker compose up -d
   docker compose ps   # db와 mediamtx 두 줄이 Up이면 된다
   ```

   `LAN_IP`를 바꾼 뒤에는 `docker compose up -d`를 다시 실행하면 MediaMTX가 새 값으로 다시 만들어진다.

4. 앱을 실행하고 브라우저에서 http://localhost:8080 을 연다. 표는 서버가 켜질 때 자동으로 만든다.

   ```bash
   dx serve --platform web
   ```

   8080번 포트를 다른 프로그램이 쓰고 있으면 `--port`로 바꾼다. 이때는 아래 주소와 터널 명령의 8080도 같은 번호로 바꿔 읽는다.

   ```bash
   dx serve --platform web --port 8090
   ```

5. (라이브 송출을 해 볼 때) 다른 터미널에서 Cloudflare 터널을 연다. 자세한 내용은 아래 "휴대폰 접속 환경"에 있다.

   ```bash
   cloudflared tunnel --url http://localhost:8080
   ```

6. (후원을 해 볼 때) 토스페이먼츠 테스트 키를 받아 `.env`에 넣고 4번의 `dx serve`를 다시 켠다. 받는 법은 아래 "토스페이먼츠 테스트 키 받기"에 있다. 키가 없어도 서버는 켜지고, 후원 칸에 "후원 기능을 쓰려면 토스 테스트 키가 필요해요"만 보인다.

### 환경 변수

| 이름 | 필수 | 예시 / 기본값 | 뜻 |
|---|---|---|---|
| `DATABASE_URL` | 예 | `postgres://chzzk:chzzk@localhost:5433/chzzk` | PostgreSQL 접속 주소 |
| `DATA_DIR` | 아니요 | 기본 `./data` | 영상 보관 폴더. 안에 `videos/`와 업로드 중 임시 파일 `tmp/`가 생긴다. |
| `MAX_UPLOAD_BYTES` | 아니요 | 기본 `2147483648` (2 GiB) | 업로드 최대 크기(바이트) |
| `MEDIAMTX_WEBRTC_URL` | 아니요 | 기본 `http://localhost:8889` | 우리 서버가 송출·시청 연결 요청(WHIP/WHEP)을 넘길 MediaMTX 주소 |
| `MEDIAMTX_API_URL` | 아니요 | 기본 `http://localhost:9997` | 상태 감시기가 "지금 영상이 들어오는 경로" 목록을 읽을 MediaMTX 관리 API 주소 |
| `LIVE_PATH_PREFIX` | 아니요 | 기본 `live` | MediaMTX 경로 앞부분(방송 3번 → `live/3`). 개발할 때 여러 작업 폴더가 MediaMTX 하나를 함께 쓸 때만 바꾼다. |
| `LAN_IP` | 예 (`docker compose`) | `192.168.0.10` | 이 컴퓨터의 와이파이 IP. 앱이 아니라 `docker compose`가 읽어 MediaMTX에 넘긴다(`MTX_WEBRTCADDITIONALHOSTS`). Docker 컨테이너 안에서는 컴퓨터의 와이파이 IP가 보이지 않기 때문이다. |
| `IP`, `PORT` | 아니요 | Dioxus 기본값 | 서버가 받을 주소와 포트 |
| `TOSS_CLIENT_KEY` | 아니요 (후원에 필요) | `test_ck_여기에_내_테스트_클라이언트_키` | 토스페이먼츠 API 개별 연동 **테스트** 클라이언트 키. 브라우저가 결제창을 열 때 쓴다(원래 공개해도 되는 키). |
| `TOSS_SECRET_KEY` | 아니요 (후원에 필요) | `test_sk_여기에_내_테스트_시크릿_키` | 같은 상점의 **테스트** 시크릿 키. 서버가 승인·조회 API를 부를 때만 쓰고 브라우저로는 보내지 않는다. |
| `TOSS_API_URL` | 아니요 | 기본 `https://api.tosspayments.com` | 토스 API 주소. 자동 테스트와 로컬 확인에서 가짜 토스 서버로 바꿀 때만 쓴다. |
| `TOSS_TEST_FAIL_CODE` | 아니요 | 비어 있음(끔). 예: `REJECT_CARD_PAYMENT` | 넣으면 승인 요청에 토스 테스트 헤더 `TossPayments-Test-Code`를 붙여 일부러 실패시킨다. 실패 화면을 확인할 때만 쓴다. 토스는 테스트 키일 때만 이 헤더를 따른다. |

토스 키는 **둘 다 넣거나 둘 다 비운다.** 둘 다 비우면 후원 기능만 꺼진 채로 켜진다. 하나만 넣거나 `test_`로 시작하지 않는 키(라이브 키 등)를 넣으면 서버가 켜지지 않고 이유를 알려 준다(오류 문구에 키 값은 넣지 않는다). 예를 들면 `TOSS_SECRET_KEY는 토스 테스트 키(test_로 시작)여야 합니다. 이 서버는 실제 결제를 하지 않습니다`다.

`.env` 예시(토스 키 두 줄은 자리표시자다. 아래 "토스페이먼츠 테스트 키 받기"에서 받은 내 키로 바꾼다):

```bash
DATABASE_URL=postgres://chzzk:chzzk@localhost:5433/chzzk
DATA_DIR=./data
MAX_UPLOAD_BYTES=2147483648
MEDIAMTX_WEBRTC_URL=http://localhost:8889
MEDIAMTX_API_URL=http://localhost:9997
LAN_IP=192.168.0.10
TOSS_CLIENT_KEY=test_ck_여기에_내_테스트_클라이언트_키
TOSS_SECRET_KEY=test_sk_여기에_내_테스트_시크릿_키
# 실패 화면을 볼 때만 앞의 #을 지운다
# TOSS_TEST_FAIL_CODE=REJECT_CARD_PAYMENT
```

`.env.example`, `docker-compose.yml`의 값은 모두 내 컴퓨터에서만 쓰는 개발용 값이다. 실제 비밀 값은 저장소에 없고, `.env`와 보관 폴더(`/data`)는 git에서 제외한다. **토스 키는 `.env`에만 두고 저장소에 올리지 않는다.** `.env.example`의 토스 키 줄은 주석 처리된 자리표시자다. 3단계에서 새로 생긴 환경 변수는 없었고, 4단계에서 위 `TOSS_` 네 개가 생겼다. 로그인 유지 기간(7일), 아이디·비밀번호·댓글 규칙, 후원 금액·메시지 규칙, 주문서 만료 시간(30분)은 코드에 상수로 있다. 세션 값은 로그인할 때마다 서버가 새로 만들며 저장소나 설정 파일에 들어가지 않는다.

## 토스페이먼츠 테스트 키 받기

후원 결제에는 토스페이먼츠의 **API 개별 연동 테스트 키** 한 쌍이 필요하다. 사업자 등록이나 계약 없이 이메일 가입만으로 받을 수 있고, 테스트 키로 한 결제는 실제로 돈이 나가지 않는다.

1. https://app.tosspayments.com/signup 에서 가입한다. 가입하면 "개발 연동 체험 상점"이 생긴다.
2. 개발자센터의 API 키 화면 https://developers.tosspayments.com/my/api-keys 를 연다.
3. **"API 개별 연동 키"** 칸의 테스트 키 두 개를 복사한다.
   - 클라이언트 키: `test_ck_`로 시작한다 → `.env`의 `TOSS_CLIENT_KEY`
   - 시크릿 키: `test_sk_`로 시작한다 → `.env`의 `TOSS_SECRET_KEY`
   - 같은 화면의 **결제위젯 연동 키**(`test_gck_`, `test_gsk_`)는 쓰지 않는다. 위젯 키는 결제위젯이라는 다른 연동 방식의 키라서, 결제창(API 개별 연동)으로 결제하는 이 서비스와 짝이 맞지 않는다([ADR 0007](docs/adr/0007-donations-via-toss-test-mode.md)).
   - `live_`로 시작하는 라이브 키는 넣지 않는다. 넣으면 서버가 켜지지 않는다.
4. `.env`에 두 줄을 넣고 `dx serve`를 다시 켠다. 서버 로그에 "TOSS_CLIENT_KEY·TOSS_SECRET_KEY가 없어 후원 기능을 끈 채로 켭니다."가 **나오지 않으면** 후원 기능이 켜진 것이다. 상세 화면의 후원 칸에 금액 버튼과 "후원하기"가 보인다.

토스 문서에 예전에 실려 있던 공용 테스트 키는 2026년 11월부터 쓸 수 없다. 내 계정에서 받은 키를 쓴다. 개발자센터에서는 내가 한 테스트 결제를 "테스트 결제내역"(https://developers.tosspayments.com/my/payment-logs)에서 볼 수 있다. 시크릿 키가 밖에 알려졌으면 같은 화면에서 다시 발급받는다.

## 휴대폰 접속 환경 (라이브 송출)

휴대폰으로 송출하려면 두 가지가 필요하다.

1. **HTTPS 주소**: 휴대폰 브라우저는 `https://` 주소(또는 `localhost`)에서만 카메라를 쓰게 해 준다. `http://192.168.x.x:8080`으로 들어오면 송출 화면에 "HTTPS 주소로 접속해야 해요" 안내가 나온다. 그래서 Cloudflare 무료 터널로 HTTPS 주소를 만든다. Cloudflare 계정은 필요 없다.
2. **같은 와이파이**: 휴대폰과 컴퓨터를 같은 와이파이에 연결한다. 휴대폰의 모바일 데이터(LTE·5G)로는 송출되지 않는다.

### cloudflared 설치

```bash
# macOS
brew install cloudflared
cloudflared --version
```

다른 운영체제는 [Cloudflare 문서](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/downloads/)에서 설치 파일을 받는다.

### 터널 실행

앱(`dx serve`)을 켜 둔 채 다른 터미널에서 실행한다.

```bash
cloudflared tunnel --url http://localhost:8080
```

몇 초 뒤 출력 중간에 아래처럼 생긴 주소가 나온다. 이 주소를 휴대폰 브라우저에서 연다.

```
Your quick Tunnel has been created! Visit it at (it may take some time to be reachable):
https://<무작위 단어들>.trycloudflare.com
```

- 주소는 터널을 실행할 때마다 바뀐다. 주소가 바뀌어도 앱이나 `.env`는 고칠 필요가 없다.
- 터널을 끄려면 그 터미널에서 Ctrl+C를 누른다.
- 처음 몇 초는 주소가 열리지 않을 수 있다. 잠시 뒤 새로고침한다.
- 컴퓨터에서 시청할 때는 터널 없이 http://localhost:8080 을 써도 된다. 터널 주소로 시청해도 된다.
- **로그인은 주소마다 따로다.** 브라우저는 주소(터널 주소, `localhost`)마다 쿠키를 따로 둔다. 컴퓨터의 `localhost`에서 로그인했어도 휴대폰의 터널 주소에서는 다시 로그인해야 한다. 터널 주소가 바뀌어도(터널을 다시 실행하면) 다시 로그인한다. 아이디와 비밀번호는 같으니 새로 가입할 필요는 없다.

## 카메라·마이크 권한

송출 화면(`/live/new`)에 들어가면 브라우저가 카메라와 마이크 사용을 묻는다. 둘 다 허용해야 방송을 시작할 수 있다.

### iOS Safari

- **처음 허용**: 터널 주소로 송출 화면을 열면 "카메라 및 마이크에 접근하려고 합니다" 창이 뜬다. "허용"을 누른다.
- **거절했을 때 다시 허용**
  1. 주소창 왼쪽의 "가가"(또는 페이지 설정) 아이콘을 누른다.
  2. "웹 사이트 설정"에서 카메라와 마이크를 "허용"(또는 "묻기")으로 바꾼다.
  3. 페이지를 새로고침한다.
- 위 메뉴에서 바꿀 수 없으면 설정 앱 → 앱 → Safari → (웹 사이트 설정의) 카메라, 마이크를 "묻기"나 "허용"으로 바꾼다. iOS 버전에 따라 설정 → Safari 아래에 있다.
- Safari는 "묻기"일 때 같은 주소에서도 다시 물을 수 있다. 터널 주소가 바뀌면 다른 사이트로 보고 처음부터 다시 묻는다.

### Android Chrome

- **처음 허용**: 송출 화면을 열면 "카메라 및 마이크를 사용하려고 합니다" 창이 뜬다. "이번 방문 동안 허용" 또는 "앱 사용 중에만 허용"을 누른다.
- **거절했을 때 다시 허용**
  1. 주소창 왼쪽의 사이트 정보 아이콘(자물쇠 또는 조절 아이콘)을 누른다.
  2. "권한"(또는 "사이트 설정")에서 카메라와 마이크를 "허용"으로 바꾼다.
  3. 페이지를 새로고침한다.
- 그래도 안 되면 휴대폰의 설정 → 애플리케이션 → Chrome → 권한에서 카메라와 마이크가 허용되어 있는지 확인한다. 휴대폰 자체가 Chrome의 카메라 사용을 막고 있으면 사이트 권한만으로는 쓸 수 없다.

권한이 없으면 송출 화면에 "카메라·마이크 권한이 없어 방송을 시작할 수 없어요…" 안내가 나오고 방송은 시작되지 않는다. 다른 앱(카메라, 영상 통화 등)이 카메라를 쓰고 있으면 "카메라를 다른 앱이 쓰고 있어요" 안내가 나온다. 그 앱을 닫고 다시 시도한다.

## 직접 확인 절차

### 1단계: 녹화 방송

준비: 재생해 볼 MP4 파일 하나. 휴대폰으로 찍은 영상이나 가지고 있는 MP4를 쓰면 된다. 없으면 ffmpeg로 10초짜리 시험 영상을 만들 수 있다.

```bash
ffmpeg -f lavfi -i testsrc=duration=10:size=640x360:rate=24 -f lavfi -i sine=frequency=440:duration=10 -c:v libx264 -pix_fmt yuv420p -c:a aac -movflags +faststart -shortest sample.mp4
```

3단계부터 등록에는 로그인이 필요하다. 아래 2번에서 "녹화 올리기"를 누르면 로그인 화면이 먼저 나오니, "회원가입"으로 아이디를 하나 만들면(가입하면 바로 로그인된다) 등록 화면으로 돌아온다.

1. **빈 목록**: http://localhost:8080 을 열면 "아직 방송이 없습니다"와 등록 버튼이 보인다.
2. **등록**: 머리글의 "녹화 올리기"를 누르고(로그인하지 않았으면 로그인·가입 뒤 돌아온다) 제목과 MP4 파일을 골라 "등록"을 누른다. 진행률이 100%까지 오른 뒤 새 방송의 상세 화면으로 이동한다.
3. **거절**: 등록 화면에서 제목을 비우거나, MP4가 아닌 파일을 골라 등록하면 화면에 이유가 나오고 방송이 생기지 않는다.
4. **목록**: 첫 화면에 방금 등록한 방송이 카드로 맨 앞에 보인다. 하나 더 등록하면 새 방송이 맨 앞에 온다.
5. **상세**: 카드를 누르면 `/broadcasts/번호` 상세 화면이 나오고 제목과 등록 시각이 보인다. 이 주소를 새 창에 붙여 넣어도 같은 방송이 나온다.
6. **재생과 건너뛰기**: 재생 버튼을 누르면 영상이 재생된다. 재생 막대의 중간을 누르면 그 지점으로 바로 이동한다.
7. **없는 방송**: http://localhost:8080/broadcasts/999999 를 열면 "방송을 찾을 수 없습니다"가 보인다.
8. **재시작 뒤 유지**: `dx serve`를 멈췄다가(Ctrl+C) 다시 실행한다. DB도 다시 띄워 보려면 `docker compose down` 뒤 `docker compose up -d`를 한다(`-v`를 붙이면 데이터가 지워지므로 붙이지 않는다). 목록과 상세 화면에 방송이 그대로 있고 영상도 재생된다.

#### 선택 확인: 휴대폰에서 등록과 재생

컴퓨터와 휴대폰이 같은 와이파이에 있을 때, 다른 기기에서도 들어올 수 있게 서버를 띄운다.

```bash
dx serve --platform web --addr 0.0.0.0
```

컴퓨터의 내부 IP(맥: 시스템 설정 → Wi-Fi → 세부사항)를 확인하고, 휴대폰 브라우저에서 `http://<컴퓨터 IP>:8080`을 연다. 등록 화면에서 갤러리의 MP4 영상을 골라 등록하고, 상세 화면에서 재생해 본다. 영상 재생기에는 `playsinline`을 넣어 iOS Safari에서도 화면 안에서 재생된다. 아래 라이브 송출과 달리 녹화 방송 등록에는 HTTPS가 필요 없지만, 터널 주소로 들어와도 똑같이 된다.

### 2단계: 라이브 방송

준비

- 위 "실행 방법" 1~5단계: `.env`의 `LAN_IP`, `docker compose up -d`, `dx serve --platform web`, `cloudflared tunnel --url http://localhost:8080`
- 휴대폰과 컴퓨터를 같은 와이파이에 연결한다.
- 휴대폰 브라우저(iOS Safari 또는 Android Chrome)에서 터널의 `https://…trycloudflare.com` 주소를 연다.
- 3단계부터 라이브 시작에는 로그인이 필요하다. 휴대폰의 터널 주소에서 로그인한다(컴퓨터의 `localhost`에서 한 로그인과는 따로다). 아직 가입하지 않았으면 "회원가입"으로 아이디를 만든다.

1. **휴대폰에서 송출 시작**
   1. 휴대폰에서 머리글의 "라이브 시작"을 누른다. 로그인하지 않았으면 로그인 화면이 나오고, 로그인하면 송출 화면으로 돌아온다.
   2. 카메라·마이크 권한을 묻는 창에서 허용한다. 후면 카메라 미리보기가 나온다. 미리보기에서는 내 목소리가 다시 나오지 않는다.
   3. 제목을 넣고 "방송 시작"을 누른다. 잠깐 "연결하는 중…"이 보인 뒤 빨간 LIVE 표시, "방송 중입니다", 시청 주소가 나온다.
   4. 제목을 비우고 시작하면 이유가 나오고 시작되지 않는다.
2. **컴퓨터의 "지금 라이브"에서 시청**
   1. 컴퓨터에서 http://localhost:8080 을 연다(이미 열려 있으면 5초 안에 저절로 갱신된다).
   2. 맨 위 "지금 라이브" 칸과 전체 목록에 방금 시작한 방송이 빨간 LIVE 표시, 시작 시각과 함께 보인다.
   3. 카드를 누르면 휴대폰 카메라 영상이 1초 안팎의 지연으로 나온다. 처음에는 소리가 꺼져 있으니 "소리 켜기"를 누른다.
   4. 휴대폰 송출 화면의 "복사"로 복사한 시청 주소를 다른 기기에서 열어도 같은 방송이 나온다.
3. **카메라 전환**: 휴대폰에서 "카메라 전환"을 누른다. 컴퓨터의 시청 화면이 끊기지 않고 전면 카메라 영상으로 바뀐다. 다시 누르면 후면으로 돌아간다.
4. **송출 종료**
   1. 휴대폰에서 "방송 종료"를 누른다. "방송을 종료했습니다"가 나오고 카메라가 꺼진다.
   2. 컴퓨터의 시청 화면에 몇 초(최대 5초 남짓) 안에 "방송이 종료되었습니다"가 나온다.
   3. 목록에서는 "지금 라이브" 칸이 사라지고(다른 방송 중인 방송이 없을 때), 전체 목록의 카드 표시가 "종료"로 바뀐다.
   4. 종료된 방송의 상세 화면에는 시작 시각과 방송한 시간이 나온다.
5. **송출 화면을 닫아 자동 종료**
   1. 1번처럼 새 방송을 시작하고, 컴퓨터에서 시청 화면을 띄워 둔다.
   2. 휴대폰에서 송출 중인 브라우저 탭을 닫는다.
   3. 몇 초 안에 컴퓨터의 시청 화면에 "방송이 종료되었습니다"가 나오고, 목록의 표시가 "종료"로 바뀐다.

### 3단계: 로그인·권한과 댓글

창 세 개로 세 사람을 흉내 낸다. 시크릿 창끼리는 쿠키를 함께 쓰는 브라우저가 있으니, 시크릿 창 두 개가 필요할 때는 서로 다른 브라우저(예: Chrome 시크릿 창과 Safari 개인 정보 보호 창)를 쓴다.

| 창 | 사람 | 준비 |
|---|---|---|
| 일반 창 | 사용자 A (소유자) | http://localhost:8080 에서 "로그인" → "회원가입"으로 `usera`를 만든다. |
| 시크릿 창 | 사용자 B (다른 사용자) | 같은 주소에서 `userb`를 만든다. |
| 또 다른 시크릿 창 | 비로그인 | 같은 주소를 열기만 한다. |

> 한 브라우저 안에서 일반 창 두 개를 쓰면 쿠키를 함께 써서 같은 사람이 된다. 브라우저 쿠키는 포트를 가리지 않으므로 `localhost:8080`과 `localhost:8090`도 같은 쿠키를 쓴다. 대신 `http://localhost:8080`과 `http://127.0.0.1:8080`은 다른 주소로 보므로 두 사용자로 나눠 쓸 수 있다.

1. **회원가입·로그인·로그아웃** (사용자 A 창)
   1. 가입 화면에서 아이디 `a`(1자)나 비밀번호 `short`(5자)로 가입하면 이유가 나오고 가입되지 않는다. B 창에서 `UserA`(대소문자만 다름)로 가입하면 "이미 쓰는 아이디예요"가 나온다.
   2. 제대로 가입하면 바로 로그인되고, 머리글에 "usera님"과 "로그아웃"이 보인다.
   3. "로그아웃"을 누르면 머리글이 "로그인"으로 바뀐다. 틀린 비밀번호로 로그인하면 "아이디 또는 비밀번호가 맞지 않아요"가 나온다. 맞는 비밀번호로 다시 로그인한다.
2. **로그인이 필요한 화면** (비로그인 창)
   1. "녹화 올리기"나 "라이브 시작"을 누르면 로그인 화면(`/login?next=…`)으로 간다. 여기서 로그인하면 누르려던 화면으로 돌아온다(확인 뒤 다시 로그아웃해 비로그인으로 돌려 둔다).
   2. 주소창에 `http://localhost:8080/login?next=https://example.com` 을 넣고 로그인하면 바깥 사이트가 아니라 첫 화면으로 간다.
3. **등록과 소유자** (사용자 A 창): 녹화 방송 하나를 등록한다. 목록 카드와 상세 화면에 `usera`가 보인다. 1·2단계에서 만든 방송이 있으면 "익명"으로 보인다.
4. **제목 수정·삭제 버튼**
   1. A 창의 그 방송 상세 화면에는 "제목 수정"과 "삭제"가 보인다. B 창과 비로그인 창에서 같은 주소를 열면 두 버튼이 없다.
   2. A 창에서 "제목 수정"을 누르고 제목을 바꿔 "저장"한다. 제목을 비우고 저장하면 이유가 나온다. B 창을 새로고침하면 새 제목이 보인다.
   3. "익명" 방송의 상세 화면에는 A 창에서도 버튼이 없다.
5. **댓글**
   1. 비로그인 창의 상세 화면 아래에는 댓글 입력 칸 대신 "로그인하고 댓글을 남겨 보세요"와 로그인 링크가 보인다. 댓글 목록은 보인다.
   2. A 창에서 댓글을 쓴다. 목록 끝에 `usera`, 쓴 시각과 함께 바로 나온다. 빈 칸(공백뿐인 글 포함)으로 등록하면 "댓글을 입력해 주세요"가 나오고 등록되지 않는다. 입력 칸은 300자까지만 받고, 화면을 거치지 않고 더 긴 글을 보내면 서버가 400으로 거절한다.
   3. B 창에서 댓글을 쓴다. A 창에는 A의 댓글에만, B 창에는 B의 댓글에만 "삭제"가 보인다. B 창에서 자기 댓글을 지우면 사라진다.
6. **라이브 시작·송출·종료** (컴퓨터만으로도 된다. 카메라가 있는 노트북이면 `localhost`에서 HTTPS 없이 카메라를 쓸 수 있다. 휴대폰으로 하려면 위 "2단계: 라이브 방송"처럼 터널 주소에서 A로 로그인한다)
   1. A 창에서 "라이브 시작"으로 방송을 시작한다. B 창과 비로그인 창의 "지금 라이브"에 `usera`의 방송이 보이고 시청된다.
   2. 시청 중인 B 창과 비로그인 창의 댓글이 3초 안에 새 댓글을 따라온다(A 창에서 댓글을 써 본다).
   3. A 창에서 방송 중에 "제목 수정"으로 제목을 바꾸면 B 창의 시청 화면에 5초 안에 반영된다.
   4. A가 송출 화면 탭은 그대로 두고 다른 탭에서 그 방송의 상세 화면을 열면 "방송 종료"가 보인다. B 창과 비로그인 창에는 없다. A의 "방송 종료"를 누르면 모든 창에 몇 초 안에 "방송이 종료되었습니다"가 나온다.
   5. 종료된 라이브 방송에도 댓글을 쓸 수 있다.
7. **삭제**
   1. A 창에서 "삭제"를 누르면 "정말 삭제할까요?"가 뜬다. "취소"하면 그대로다.
   2. 확인하면 목록으로 가고 방송이 사라진다. B 창에서 그 주소를 새로고침하면 "방송을 찾을 수 없습니다"(404)가 나온다. 녹화 방송 상세 화면은 저절로 다시 묻지 않으므로 새로고침해야 바뀐다.
   3. 방송 중인 라이브 방송을 지우면 송출이 끊긴 뒤 사라진다. 그 방송을 시청 중이던 B 창에는 새로고침하지 않아도 몇 초 안에 "방송을 찾을 수 없습니다"가 나온다.

### 화면을 거치지 않는 요청으로 확인 (`curl`)

화면에서 버튼을 숨기는 것만으로는 막을 수 없다. 아래처럼 요청을 직접 보내도 서버가 거절하는지 본다. `-c 파일`은 받은 쿠키를 그 파일에 저장하고, `-b 파일`은 그 쿠키를 붙여 보낸다. 파일 하나가 브라우저 한 개(사용자 한 명)인 셈이다. `-w '%{http_code}'`는 상태 코드를 마지막에 찍는다.

`curl`은 `Origin`이나 `Sec-Fetch-Site` 헤더를 붙이지 않으므로 다른 사이트 요청 막기(CSRF)에 걸리지 않고 쿠키 규칙만 따른다([ADR 0006](docs/adr/0006-server-sessions-in-cookies.md)). 앱을 8080이 아닌 포트로 띄웠으면 `B`를 바꾼다. 아래 방송 번호(`1`, `2`)와 댓글 번호(`1`)는 빈 DB에서 시작했을 때의 값이니, 이미 방송이 있으면 응답의 `id`로 바꿔 넣는다.

```bash
B=http://localhost:8080
J='Content-Type: application/json'

# 사용자 A, B 가입(이미 있으면 /api/auth/login 으로 같은 내용을 보내 쿠키를 받는다)
curl -s -w ' %{http_code}\n' -c a.txt -H "$J" -d '{"username":"usera","password":"password-a1"}' $B/api/auth/signup
# {"username":"usera"} 201
curl -s -w ' %{http_code}\n' -c b.txt -H "$J" -d '{"username":"userb","password":"password-b1"}' $B/api/auth/signup
# {"username":"userb"} 201
curl -s -w ' %{http_code}\n' -b a.txt $B/api/auth/me
# {"username":"usera"} 200

# 로그인 없이 등록·라이브 시작 → 401
curl -s -w ' %{http_code}\n' -F title=몰래 -F video=@sample.mp4 $B/api/broadcasts
# {"code":"login_required","message":"로그인이 필요해요."} 401
curl -s -w ' %{http_code}\n' -H "$J" -d '{"title":"몰래"}' $B/api/live
# {"code":"login_required",...} 401

# A가 녹화 방송(1번)과 라이브 방송(2번)을 만든다
curl -s -w ' %{http_code}\n' -b a.txt -F title=A의방송 -F video=@sample.mp4 $B/api/broadcasts
# {"id":1} 201
curl -s -w ' %{http_code}\n' -b a.txt -H "$J" -d '{"title":"A 라이브"}' $B/api/live
# {"id":2} 201

# B가 A의 방송을 고치거나 지우거나 끄려 한다 → 403
curl -s -w ' %{http_code}\n' -b b.txt -X PATCH -H "$J" -d '{"title":"B가 바꿈"}' $B/api/broadcasts/1
# {"code":"forbidden","message":"권한이 없어요."} 403
curl -s -w ' %{http_code}\n' -b b.txt -X DELETE $B/api/broadcasts/1
# {"code":"forbidden",...} 403
curl -s -w ' %{http_code}\n' -b b.txt -X POST $B/api/live/2/end
# {"code":"forbidden",...} 403
curl -s -w ' %{http_code}\n' -b b.txt -H 'Content-Type: application/sdp' --data-binary 'v=0' $B/api/live/2/whip
# {"code":"forbidden",...} 403

# 쿠키 없이 같은 요청 → 401
curl -s -w ' %{http_code}\n' -X DELETE $B/api/broadcasts/1
# {"code":"login_required",...} 401
curl -s -w ' %{http_code}\n' -X POST $B/api/live/2/end
# {"code":"login_required",...} 401

# A의 쿠키라도 다른 사이트에서 온 요청이면 → 403 (CSRF 막기)
curl -s -w ' %{http_code}\n' -b a.txt -H 'Origin: https://evil.example' -X DELETE $B/api/broadcasts/1
# {"code":"forbidden",...} 403

# 댓글: 쿠키 없이 쓰기 → 401, A가 쓰기 → 201, B가 A의 댓글 지우기 → 403
curl -s -w ' %{http_code}\n' -H "$J" -d '{"body":"안녕"}' $B/api/broadcasts/1/comments
# {"code":"login_required",...} 401
curl -s -w ' %{http_code}\n' -b a.txt -H "$J" -d '{"body":"A의 댓글"}' $B/api/broadcasts/1/comments
# {"id":1,"author":"usera","body":"A의 댓글",...,"mine":true} 201
curl -s -w ' %{http_code}\n' -b b.txt -X DELETE $B/api/comments/1
# {"code":"forbidden",...} 403
curl -s -w ' %{http_code}\n' -X DELETE $B/api/comments/1
# {"code":"login_required",...} 401
curl -s -w ' %{http_code}\n' $B/api/broadcasts/1/comments
# [{"id":1,"author":"usera",...,"mine":false}] 200   (누구나 읽는다. 쿠키가 없으니 mine은 false)

# 소유자 A는 된다
curl -s -w ' %{http_code}\n' -b a.txt -X PATCH -H "$J" -d '{"title":"고친 제목"}' $B/api/broadcasts/1
# {"id":1,"title":"고친 제목"} 200
curl -s -w ' %{http_code}\n' -b a.txt -X DELETE $B/api/comments/1
#  204
curl -s -w ' %{http_code}\n' -b a.txt -X DELETE $B/api/broadcasts/1
#  204
curl -s -o /dev/null -w '%{http_code}\n' $B/api/broadcasts/1/video
# 404   (영상도 지워졌다)
curl -s -w ' %{http_code}\n' -b a.txt -X POST $B/api/live/2/end
#  204

# 로그아웃하면 그 쿠키는 바로 무효
curl -s -w ' %{http_code}\n' -b a.txt -X POST $B/api/auth/logout
#  204
curl -s -w ' %{http_code}\n' -b a.txt $B/api/auth/me
# {"username":null} 200
curl -s -w ' %{http_code}\n' -b a.txt -H "$J" -d '{"body":"x"}' $B/api/broadcasts/2/comments
# {"code":"login_required",...} 401
```

`sample.mp4`는 위 "1단계: 녹화 방송"의 ffmpeg 명령으로 만든 파일이다. 확인이 끝나면 `rm a.txt b.txt`로 쿠키 파일을 지운다. 응답의 `created_at` 같은 시각 값은 실행할 때마다 다르다.

### 4단계: 후원

준비

- 위 "실행 방법" 1~4단계와 6단계: `.env`에 내 토스 **테스트** 키 두 개를 넣고 `dx serve --platform web`을 켠다. 컴퓨터 브라우저만으로 된다(휴대폰은 필요 없다).
- 3단계처럼 창 두 개로 두 사람을 흉내 낸다. 일반 창은 방송 소유자 A(`usera`), 다른 브라우저의 시크릿 창은 후원자 B(`userb`)다. 위 `curl` 절에서 만든 아이디라면 비밀번호는 `password-a1`, `password-b1`이다.
- A 창에서 녹화 방송을 하나 등록한다. 그 방송 상세 화면 주소(`/broadcasts/번호`)의 번호를 아래에서 "방송 번호"로 쓴다.

**결제창에 무엇을 넣나**: 토스 테스트 모드에는 따로 정해진 테스트 카드 번호가 없다. 결제창에서 카드사를 고르고 가지고 있는 카드 정보를 넣으면 된다. 테스트 키로 한 결제는 승인되어도 **카드에서 돈이 빠져나가지 않는다**(청구되지 않는다). 후원 칸과 결과 화면 위쪽의 "테스트 결제 · 실제로 돈이 나가지 않아요"를 확인한다. 카드 대신 결제창 안의 간편결제를 골라도 된다.

1. **화면 확인** (두 창)
   1. 비로그인 상태로 상세 화면을 열면 후원 칸에 "아직 후원이 없습니다"와 "로그인하고 후원하기"가 보인다. 누르면 로그인 화면으로 갔다가 로그인 뒤 이 방송으로 돌아온다.
   2. A 창(내 방송)에는 합계와 내역만 있고 금액 버튼과 "후원하기"가 없다. 1·2단계에서 만든 "익명" 방송에도 없다.
   3. B 창에는 1,000원·5,000원·10,000원·50,000원 버튼, "직접 입력", 메시지 칸, "후원하기"가 보인다. 직접 입력에 `999`나 `1050`을 넣고 "후원하기"를 누르면 결제창이 열리지 않고 이유가 나온다.
2. **성공** (B 창)
   1. 5,000원을 고르고 메시지 "응원해요"를 적어 "후원하기"를 누른다. 토스 결제창이 열리고 "usera님에게 후원 5,000원"이 보인다.
   2. 카드 정보를 넣고 결제를 마친다. `/donations/success?paymentKey=…&orderId=…&amount=5000` 주소로 돌아와 잠깐 "결제를 확인하는 중…" 뒤 "후원이 완료되었습니다", "5,000원", "N번 방송에 후원했어요."가 나온다.
   3. "방송으로 돌아가기"를 누르면 후원 칸에 "총 5,000원 · 1건"과 `userb`, 5,000원, "응원해요", 시각이 보인다. A 창과 비로그인 창에서도 같다.
   4. 결과 화면에서 새로고침하거나 뒤로 갔다가 다시 와도 "후원이 완료되었습니다"가 그대로이고 합계는 1건 그대로다.
   5. 다음 확인을 위해 결과 화면의 주소를 복사해 둔다.
3. **실패** (B 창)
   1. `dx serve`를 멈추고(Ctrl+C) `.env`에 `TOSS_TEST_FAIL_CODE=REJECT_CARD_PAYMENT` 한 줄을 넣은 뒤 다시 켠다.
   2. 2번처럼 후원하고 결제창에서 결제를 마친다. 결과 화면에 "후원이 완료되지 않았어요"와 토스가 알려 준 거절 이유가 나온다. 서버가 승인 요청에 테스트 헤더를 붙여 토스가 카드 거절로 답했기 때문이다.
   3. "방송으로 돌아가기"를 누르면 합계와 내역이 그대로다(늘지 않는다).
   4. 끝나면 그 줄을 지우고 `dx serve`를 다시 켠다.
4. **취소** (B 창): 후원하기를 눌러 결제창을 연 뒤 결제하지 않고 결제창을 닫는다(오른쪽 위 X, 또는 결제창의 취소). 컴퓨터에서는 후원 칸 아래에 "결제를 취소했습니다."가 나오고, 휴대폰에서는 `/donations/fail` 화면에 "결제를 취소했습니다"가 나온다. 합계와 내역은 그대로다.
5. **금액 조작 거절**
   1. 2-5에서 복사한 결과 화면 주소의 `amount=5000`을 `amount=100`으로 바꿔 연다. 결과 화면은 주소의 값이 아니라 서버의 주문서 금액(5,000원)을 보여 주고, 이미 확정된 주문서라 합계는 1건 그대로다. 주소를 바꿔도 금액이 바뀌거나 후원이 하나 더 생기지 않는다.
   2. 결제하기 전의 주문서로도 해 본다. 아래 `curl` 블록의 "금액 조작" 부분처럼 B로 10,000원 주문서를 만들고, 그 응답의 `order_id`를 넣어 B 창에서 `http://localhost:8080/donations/success?paymentKey=tgen_tampered&orderId=<order_id>&amount=1000` 을 연다. "후원이 완료되지 않았어요"와 "결제 금액이 주문서와 달라요."가 나오고 합계는 그대로다. 서버는 금액이 다른 것을 보고 토스에 승인을 요청하지도 않는다.
6. **승인 통지 중복** (`curl`): 2번에서 확정된 결제의 결제 키로 같은 승인 통지를 두 번 보내고, 합계가 늘지 않는 것을 본다. 아래 `curl` 블록의 "승인 통지 중복" 부분이다.
7. (선택) **진짜 승인 통지 받기**: 토스는 웹훅 주소로 `localhost`를 받지 않으므로 공개 주소가 필요하다.
   1. 다른 터미널에서 `cloudflared tunnel --url http://localhost:8080`을 실행해 `https://…trycloudflare.com` 주소를 받는다.
   2. 개발자센터의 웹훅 화면 https://developers.tosspayments.com/my/webhooks 에서 "웹훅 등록하기"를 누르고, URL에 `https://<터널 주소>/api/payments/toss-webhook`, 이벤트에 `PAYMENT_STATUS_CHANGED`를 고른다.
   3. 2번처럼 한 번 더 후원한다. 개발자센터의 웹훅 전송 기록에 이 결제의 통지가 200으로 남고, 합계는 이 후원 한 건만큼만 는다(결과 화면과 통지가 둘 다 와도 한 번).
   4. 전송 기록의 "다시 시도"로 같은 통지를 다시 보내도 합계는 그대로다.
   5. 터널 주소는 실행할 때마다 바뀌므로, 터널을 다시 켜면 웹훅 URL도 다시 등록한다. 터널 주소로 접속한 브라우저에서 후원하면 결과 화면도 터널 주소로 돌아온다(로그인은 주소마다 따로다).

#### 화면을 거치지 않는 후원 요청 (`curl`)

`B`는 앱 주소, `N`은 A의 방송 번호(빈 DB에서 녹화 방송 하나를 등록했으면 `1`)다. 쿠키 파일은 3단계 `curl` 절과 같은 방식이다. 3단계 절을 끝까지 했다면 `a.txt`는 로그아웃됐으니 아래처럼 다시 로그인한다.

```bash
B=http://localhost:8080
J='Content-Type: application/json'
N=1

curl -s -w ' %{http_code}\n' -c a.txt -H "$J" -d '{"username":"usera","password":"password-a1"}' $B/api/auth/login
# {"username":"usera"} 200
curl -s -w ' %{http_code}\n' -c b.txt -H "$J" -d '{"username":"userb","password":"password-b1"}' $B/api/auth/login
# {"username":"userb"} 200

# 후원 거절: 비로그인 401, 내 방송 400, 100원 단위가 아님 400
curl -s -w ' %{http_code}\n' -H "$J" -d '{"amount":5000}' $B/api/broadcasts/$N/donations
# {"code":"login_required","message":"로그인이 필요해요."} 401
curl -s -w ' %{http_code}\n' -b a.txt -H "$J" -d '{"amount":5000}' $B/api/broadcasts/$N/donations
# {"code":"own_broadcast","message":"내 방송에는 후원할 수 없어요."} 400
curl -s -w ' %{http_code}\n' -b b.txt -H "$J" -d '{"amount":1050}' $B/api/broadcasts/$N/donations
# {"code":"amount_not_step","message":"후원 금액은 100원 단위로 정해 주세요."} 400

# 금액 조작: B가 10,000원 주문서를 만들고, 돌아온 금액을 1,000원으로 바꿔 승인 확인을 부른다
curl -s -w ' %{http_code}\n' -b b.txt -H "$J" -d '{"amount":10000}' $B/api/broadcasts/$N/donations
# {"order_id":"don_…","amount":10000,"order_name":"usera님에게 후원 10,000원","client_key":"test_ck_…"} 201
O2=<위 응답의 order_id>
curl -s -w ' %{http_code}\n' -H "$J" -d '{"payment_key":"tgen_tampered","order_id":"'$O2'","amount":1000}' $B/api/donations/confirm
# {"status":"failed","broadcast_id":1,"amount":10000,"code":"amount_mismatch","message":"결제 금액이 주문서와 달라요."} 200
# 이 주문서는 실패로 끝났다. 원래 금액으로 다시 불러도 실패 그대로이고 후원은 생기지 않는다.

# 승인 통지 중복: 2번(성공)에서 확정된 결제의 결제 키(P)와 주문 번호(O)를 넣는다
P=<결제 키>
O=<주문 번호>
curl -s $B/api/broadcasts/$N/donations
# {"total_amount":5000,"count":1,"items":[{"donor":"userb","amount":5000,"message":"응원해요",...}],"enabled":true}
NOTICE='{"eventType":"PAYMENT_STATUS_CHANGED","createdAt":"2026-11-22T10:00:00.000000","data":{"paymentKey":"'$P'","orderId":"'$O'","status":"DONE","totalAmount":5000}}'
curl -s -w ' %{http_code}\n' -H "$J" -d "$NOTICE" $B/api/payments/toss-webhook
#  200
curl -s -w ' %{http_code}\n' -H "$J" -d "$NOTICE" $B/api/payments/toss-webhook
#  200
curl -s $B/api/broadcasts/$N/donations
# {"total_amount":5000,"count":1,...}   (두 번 보내도 1건 그대로)

# 꾸며낸 통지: 없는 결제 키는 200으로 받고 무시한다
curl -s -w ' %{http_code}\n' -H "$J" -d '{"data":{"paymentKey":"tgen_forged_123"}}' $B/api/payments/toss-webhook
#  200
curl -s $B/api/broadcasts/$N/donations
# {"total_amount":5000,"count":1,...}   (그대로)
```

결제 키와 주문 번호는 둘 중 한 곳에서 찾는다.

- **DB**: 가장 최근에 확정된 주문서를 본다.

  ```bash
  docker compose exec db psql -U chzzk -d chzzk -c "SELECT order_id, payment_key, amount, status FROM donation_orders WHERE status = 'confirmed' ORDER BY id DESC LIMIT 1"
  ```

- **개발자센터**: 테스트 결제내역(https://developers.tosspayments.com/my/payment-logs)에서 방금 한 결제를 열면 결제 키(paymentKey)와 주문 번호(orderId, `don_`으로 시작)가 있다.

승인 통지를 받으면 서버는 본문의 금액·상태를 쓰지 않고, 결제 키로 토스에 다시 조회한다. 조회 결과 그 결제의 주문서가 이미 확정이면 아무것도 바꾸지 않는다. 그래서 통지 본문의 `totalAmount`를 부풀려 보내도 후원이 생기거나 금액이 바뀌지 않는다. 통지가 결과 화면보다 먼저 오거나 둘이 동시에 오는 경우는 자동 테스트(아래 "승인 통지" 묶음)에서 확인한다. 확인이 끝나면 `rm a.txt b.txt`로 쿠키 파일을 지운다.

### 화면 잠금·앱 전환 시 자동 종료

- 송출 중에 휴대폰 화면을 잠그거나, 다른 앱으로 가거나, 브라우저를 백그라운드로 보내면 휴대폰 브라우저가 카메라를 멈춘다. 영상이 끊기면 서버가 몇 초 안에 알아채고 방송을 **종료**로 바꾼다. 이것은 고장이 아니라 정해진 동작이다.
- 한 번 종료된 방송은 다시 방송 중으로 돌아가지 않는다. 계속하려면 "라이브 시작"으로 새 방송을 시작한다.
- 송출하는 동안에는 화면이 저절로 꺼지지 않게 막는다. 브라우저가 이 기능을 지원하지 않으면 "송출 중에는 화면을 켜 두세요" 안내가 나오니, 그때는 직접 화면을 켜 둔다. 휴대폰의 저전력 모드에서는 막기가 듣지 않을 수 있다.
- 와이파이가 끊겨도 같은 방식으로 종료된다.

### 잘 안 될 때

| 증상 | 확인할 것 |
|---|---|
| "HTTPS 주소로 접속해야 해요" | 휴대폰에서 `http://…` 주소로 들어왔다. 터널의 `https://…trycloudflare.com` 주소로 연다. |
| "송출 서버와 연결하지 못했어요" | 휴대폰과 컴퓨터가 같은 와이파이인지, `.env`의 `LAN_IP`가 지금 와이파이 IP와 같은지, `LAN_IP`를 바꾼 뒤 `docker compose up -d`를 다시 했는지 확인한다. 손님용 와이파이·회사 와이파이처럼 기기끼리 막힌 망이면 다른 와이파이를 쓴다. 맥의 방화벽이 Docker의 연결을 막고 있지 않은지도 본다. |
| 시청 화면이 검게 나온다 | "소리 켜기"를 누르거나 영상을 한 번 누른다. 그래도 안 나오면 새로고침한다. |
| 터널 주소가 열리지 않는다 | `dx serve`가 켜져 있는지, 터널 명령의 포트가 `dx serve`의 포트와 같은지 확인한다. 막 만든 주소는 몇 초 뒤에 열린다. |
| 서버가 "…는 토스 테스트 키(test_로 시작)여야 합니다"나 "TOSS_SECRET_KEY가 없습니다"로 켜지지 않는다 | `.env`의 토스 키가 API 개별 연동 **테스트** 키(`test_ck_`, `test_sk_`)인지, 두 줄이 다 있는지 본다. 라이브 키는 받지 않는다. 후원을 안 쓸 거면 두 줄을 다 지운다. |
| 후원 칸에 "후원 기능을 쓰려면 토스 테스트 키가 필요해요" | 서버에 토스 키가 없다. `.env`에 두 줄을 넣고 `dx serve`를 다시 켠다. |
| "후원하기"를 눌러도 결제창이 열리지 않는다 | "토스 결제 모듈을 불러오지 못했어요"면 인터넷 연결이나 광고 차단 확장 프로그램이 `js.tosspayments.com`을 막고 있지 않은지 본다. 다른 이유가 나오면 클라이언트 키가 위젯 키(`test_gck_`)가 아닌지 본다. |
| 결과 화면에 "결제 결과를 아직 확인하지 못했어요" | 서버가 토스에 닿지 못했다. 주문서는 결제 대기로 남아 있으니 잠시 뒤 결과 화면을 새로고침한다. |

## 테스트

DB 테스트는 실제 PostgreSQL이 필요하다. `#[sqlx::test]`가 테스트마다 빈 임시 DB를 만들고 끝나면 지우므로, 개발용 데이터에는 영향이 없다. 영상 보관 폴더도 테스트마다 임시 폴더를 쓴다. 라이브 방송 테스트는 진짜 MediaMTX 대신 테스트 안에서 띄우는 **가짜 MediaMTX**(작은 axum 서버)를 쓰므로, MediaMTX 컨테이너나 카메라가 없어도 된다. 후원 테스트도 같은 방식으로 **가짜 토스 서버**(`src/donations/fake_toss.rs`)를 띄워 `TOSS_API_URL` 자리에 끼우므로, 토스 키나 인터넷 연결이 없어도 된다. 가짜 토스는 받은 승인·조회 요청(헤더 포함)을 기록하고, 테스트가 정한 대답(`DONE`, 다른 금액, 카드 거절, 이미 처리됨, 내부 오류 등)을 돌려준다.

```bash
docker compose up -d
set -a; . ./.env; set +a
cargo test --no-default-features --features server
```

경고까지 오류로 다루려면(아래 결과는 이렇게 실행했다) 앞에 `RUSTFLAGS="-D warnings"`를 붙인다.

```bash
RUSTFLAGS="-D warnings" DATABASE_URL=postgres://chzzk:chzzk@localhost:5433/chzzk cargo test --no-default-features --features server
```

테스트는 서버를 띄우지 않고 HTTP 라우터에 요청을 직접 넣어, 응답과 그 뒤의 조회 결과를 본다. 상태 감시기는 "한 번 맞추기" 동작을 테스트가 직접 부르고, 지금 시각을 넘겨 30초 경과를 흉내 낸다.

4단계 테스트는 3단계의 손님(비로그인, 소유자 A, 다른 사용자 B)으로 우리 서버의 HTTP 라우터에 요청을 넣고, 응답과 그 뒤의 후원 합계·내역·주문서 상태, 가짜 토스가 받은 요청으로 판단한다. 만료 정리는 "한 번 정리" 함수를 테스트가 지금 시각을 넘겨 부른다.

3단계 테스트는 손님 세 종류로 요청을 보낸다. 쿠키 없는 비로그인 손님, 진짜 가입 API로 쿠키를 받은 소유자 A, 다른 아이디로 쿠키를 받은 다른 사용자 B다. 1·2단계 테스트는 본문을 바꾸지 않았다. 로그인이 새 전제가 되었으므로 등록 요청과 라이브 시작을 만드는 공용 도우미에서만 A의 쿠키를 붙인다. 송출 키 자체를 확인하던 2단계 테스트(키 해시 저장, 틀린 키 401)는 같은 뜻의 소유자 테스트(비로그인 401, 다른 사용자 403)로 바꿨다.

|---|---|
| 가입·로그인 | 가입하면 201과 `HttpOnly`·`SameSite=Lax` 쿠키가 오고, 그 쿠키로 `me`가 아이디를 돌려준다. 규칙 위반(128자를 넘는 비밀번호 포함) 400, 대소문자만 다른 같은 아이디 409. 로그인 200, 없는 아이디와 틀린 비밀번호는 둘 다 401에 같은 문구. 로그아웃 뒤 같은 쿠키는 `me`가 null이고 로그인이 필요한 요청은 401. 만료된 세션은 로그인으로 치지 않는다. |
