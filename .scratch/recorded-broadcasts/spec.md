# Spec: 1단계 녹화 방송 등록과 시청

Status: ready-for-agent

## Problem Statement

녹화해 둔 영상을 다른 사람에게 보여 주려면 지금은 계정을 만들고 외부 플랫폼에 올려야 한다. 로그인 없이 제목과 영상만으로 방송을 등록할 곳이 없다. 링크를 받은 사람이나 목록을 둘러보는 사람이 데스크톱이나 휴대폰 브라우저에서 바로 재생할 수 있는 곳도 없다.

이 스펙은 "치지직 만들기" 과제 4단계 중 1단계다. 이후 단계는 이 단계의 기능을 유지하며 확장한다.
- 2단계: 휴대폰 라이브 송출
- 3단계: 인증·인가와 댓글
- 4단계: 도네이션

채점은 제출한 소스와 README를 읽기만 하는 정적 평가다. 실제로 실행하거나 재생하지 않는다.

## Solution

웹 앱 하나에서 누구나 제목과 MP4 영상을 올려 방송을 등록한다.
- 등록은 원자적이다. 업로드가 끝까지 성공해야만 방송이 생긴다.
- 목록 화면은 방송을 최신순 카드로 보여 준다.
- 상세 화면은 영상을 재생하며, 중간으로 건너뛸 수 있다.
- 서버는 방송 정보(방송 번호, 제목, 영상 위치, 등록 시각)를 PostgreSQL에 저장한다.
- 원본 MP4는 변환 없이 HTTP Range 요청으로 전송한다.
- 화면에 보이는 서비스 이름은 "녹화방송"이다. 치지직의 로고, 이름, 고유 색은 쓰지 않는다.

1단계는 로컬 실행까지만 한다. 저장소 README에 다음을 적는다.
- 실행 방법
- 환경변수 예시
- 구현 범위
- 직접 확인 절차

## User Stories

1. 방문자로서, 로그인 없이 방송을 등록하고 싶다. 계정을 만들지 않고 바로 영상을 공유하기 위해서다.
2. 방문자로서, 등록할 때 제목을 입력하고 싶다. 시청자가 어떤 방송인지 알 수 있게 하기 위해서다.
3. 방문자로서, 등록할 때 내 컴퓨터에서 MP4 파일을 고르고 싶다. 녹화해 둔 영상을 그대로 올리기 위해서다.
4. 방문자로서, 휴대폰 브라우저에서도 갤러리의 영상을 골라 등록하고 싶다.
5. 방문자로서, 업로드하는 동안 진행률(%)을 보고 싶다. 큰 파일을 올릴 때 화면이 멈춘 게 아님을 알기 위해서다.
6. 방문자로서, 업로드 중에는 등록 버튼이 다시 눌리지 않기를 원한다. 같은 방송이 두 번 생기지 않게 하기 위해서다.
7. 방문자로서, 등록이 끝나면 방금 만든 방송의 상세 화면으로 이동하고 싶다. 바로 확인하고 링크를 복사하기 위해서다.
8. 방문자로서, 제목을 비웠거나 공백만 넣었을 때 등록이 거절되고 이유를 보고 싶다. 무엇을 고쳐야 하는지 알기 위해서다.
9. 방문자로서, 제목이 100자를 넘으면 등록이 거절되고 이유를 보고 싶다.
10. 방문자로서, 제목 앞뒤의 공백은 자동으로 제거되었으면 한다. 실수로 넣은 공백이 제목에 남지 않게 하기 위해서다.
11. 방문자로서, 다른 방송과 같은 제목으로도 등록할 수 있기를 원한다.
12. 방문자로서, 파일을 고르지 않고 등록하면 거절되고 이유를 보고 싶다.
13. 방문자로서, MP4가 아닌 파일을 고르면 등록이 거절되고 이유를 보고 싶다. 재생되지 않는 방송이 생기지 않게 하기 위해서다.
14. 방문자로서, 확장자만 `.mp4`로 바꾼 다른 파일도 거절되기를 원한다.
15. 방문자로서, 2 GiB(기본값)를 넘는 파일을 올리면 등록이 거절되고 이유를 보고 싶다.
16. 방문자로서, 업로드가 중간에 실패하거나 연결이 끊기면 반쯤 만들어진 방송이 목록에 남지 않기를 원한다.
17. 방문자로서, 업로드에 실패한 뒤 같은 파일로 다시 등록할 수 있기를 원한다.
18. 시청자로서, 첫 화면에서 등록된 방송 목록을 보고 싶다. 볼 만한 방송을 고르기 위해서다.
19. 시청자로서, 목록이 최신 등록순이기를 원한다. 새 방송을 먼저 보기 위해서다.
20. 시청자로서, 목록의 각 카드에서 제목과 등록 시각을 보고 싶다.
21. 시청자로서, 카드의 썸네일 자리에 빈 칸이 있어 카드 모양이 고르게 보이기를 원한다.
22. 시청자로서, 아주 긴 제목도 카드 밖으로 넘치지 않고 보이기를 원한다.
23. 시청자로서, 카드를 누르면 그 방송의 상세 화면으로 가고 싶다.
24. 시청자로서, 방송이 하나도 없을 때 "아직 방송이 없습니다" 안내와 등록 버튼을 보고 싶다.
25. 방문자로서, 어느 화면에서든 등록 화면으로 가는 버튼을 보고 싶다.
26. 시청자로서, 상세 화면에서 제목과 등록 시각을 보고 싶다.
27. 시청자로서, 상세 화면에서 영상을 재생하고 싶다.
28. 시청자로서, 영상을 끝까지 내려받지 않고도 원하는 지점으로 이동(seek)하고 싶다.
29. 시청자로서, 받은 상세 화면 링크(`/broadcasts/번호`)를 열면 바로 그 방송이 나오기를 원한다. 링크로 방송을 공유하기 위해서다.
30. 시청자로서, iOS Safari를 포함한 휴대폰 브라우저에서도 영상을 재생하고 싶다.
31. 시청자로서, 데스크톱 브라우저에서 영상을 재생하고 싶다.
32. 시청자로서, 존재하지 않는 방송 번호나 번호가 아닌 주소를 열면 "방송을 찾을 수 없습니다" 화면을 보고 싶다.
33. 시청자로서, 상세 화면에서 목록으로 돌아가고 싶다.
34. 시청자로서, 등록 시각을 한국 시간으로 보고 싶다.
35. 운영자로서, 서버를 재시작해도 방송 정보와 영상이 그대로 남아 다시 조회되기를 원한다.
36. 운영자로서, DB 주소, 영상 보관 폴더, 업로드 최대 크기를 환경변수로 정하고 싶다. 실행 환경마다 바꾸기 위해서다.
37. 운영자로서, 큰 파일이 업로드되는 중에도 서버 메모리 사용량이 파일 크기만큼 늘지 않기를 원한다.
38. 운영자로서, 영상 위치가 보관 폴더 기준의 상대 위치로 저장되기를 원한다. 나중에 폴더를 옮기거나 저장소를 바꿔도 방송 정보를 다시 쓸 필요가 없게 하기 위해서다.
39. 운영자로서, 방송 번호가 DB에서 매겨지기를 원한다. 동시에 여러 사람이 등록해도 번호가 겹치지 않게 하기 위해서다.
40. 채점자로서, README만 보고 저장소를 받아 설치하고 실행하는 방법을 알 수 있기를 원한다.
41. 채점자로서, README에서 필요한 환경변수와 예시 값을 보고 싶다. 실제 비밀 값 없이 이해하기 위해서다.
42. 채점자로서, README에서 이번 단계의 구현 범위와 하지 않은 것을 보고 싶다.
43. 채점자로서, README의 직접 확인 절차를 순서대로 읽고 싶다. 순서는 등록 → 목록 → 상세 → 재생과 건너뛰기 → 서버 재시작 → 다시 조회다.
44. 채점자로서, 1단계 시점의 코드를 정확히 보고 싶다. 나중 단계 코드가 섞이지 않게 하기 위해서다.

## Implementation Decisions

- **용어**: GLOSSARY.md의 **방송**, **영상**, **등록**, **방송 번호**를 쓴다.
  - 방송은 제목 하나와 영상 하나를 가지고, 방송과 영상은 1:1이다.
  - "업로드"는 영상 파일을 전송하는 일만 가리킨다.
- **기술**: Rust Dioxus 0.7 fullstack 크레이트 하나를 저장소 루트에 둔다. 모노레포는 쓰지 않는다(ADR 0003).
  - 단축 URL 과제와 같은 구성이다.
    - 기본 기능은 web이다.
    - server 기능에서만 서버 전용 의존성(sqlx, 환경변수 읽기 등)을 켠다.
    - 서버는 Dioxus 라우터에 axum 라우트를 덧붙인다.
  - DB는 PostgreSQL이고 sqlx 0.8로 접근한다. 앱이 시작할 때 마이그레이션을 적용한다.
  - 로컬 개발용 PostgreSQL은 Docker Compose로 띄운다.
- **모듈**:
  - **제목 규칙**: 화면과 무관한 순수 함수다. 앞뒤 공백을 지운 뒤 1~100자(문자 수 기준)여야 하고, 중복은 허용한다. 위반 이유를 한국어 메시지로 돌려준다.
  - **방송 저장소**: 방송 하나 등록(번호를 돌려줌), 목록(최신순), 번호로 하나 조회.
  - **영상 보관**: 영상 보관 폴더 아래 로컬 디스크에 둔다. 임시 파일 받기, 최종 위치로 옮기기, 지우기, 경로 찾기를 맡는다. 나중에 원격 저장소로 바꿀 수 있게 이 모듈 뒤에 숨긴다.
  - **등록 처리**: 업로드 받기, 검사, 저장을 묶어 원자적으로 처리한다.
  - **HTTP 라우트**: 등록 API와 영상 전송.
  - **화면**: 목록, 상세, 등록 페이지와 "방송을 찾을 수 없습니다" 페이지.
- **방송 번호**: `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`.
  - DB가 매기며 1부터 커진다.
  - 실패한 등록 때문에 빈 번호가 생길 수 있다.
  - 영상 파일 이름도 이 번호로 짓는다.
- **방송 정보 스키마**: 칸은 아래 넷이다.
  - 방송 번호
  - 제목: `CHECK`로 1~100자
  - 영상 키: 보관 폴더 기준 상대 위치. 예: `videos/12.mp4`
  - 등록 시각: `TIMESTAMPTZ`, 기본값은 현재 시각

  녹화 방송과 라이브 방송을 구분하는 칸은 지금 만들지 않는다. 2단계에서 마이그레이션으로 추가한다.
- **HTTP 계약**:
  - `POST /api/broadcasts`
    - multipart로 `title`과 `video`를 받는다.
    - 성공하면 201과 새 방송 번호(JSON)를 돌려준다.
    - 실패하면 상태 코드와 함께 원인 코드와 한국어 메시지(JSON)를 돌려준다.
      - 400: 제목 위반, 파일 없음, MP4 아님
      - 413: 크기 초과
    - Dioxus 서버 함수가 아니라 직접 덧붙인 axum 라우트다. 서버 함수는 본문을 메모리에 모으기 때문이다.
    - 이 라우트만 기본 본문 크기 제한을 업로드 최대 크기에 맞춰 늘린다.
  - `GET /api/broadcasts/{번호}/video`
    - 영상 파일을 전송한다.
    - Range 요청에는 206, `Content-Range`, `Accept-Ranges`로 응답한다. Range가 없으면 200과 전체 파일을 준다.
    - `Content-Type`은 `video/mp4`다.
    - 없는 번호나 번호가 아닌 값이면 404다.
    - 원본을 변환하지 않는다(ADR 0001). Range를 지원하는 검증된 파일 전송 구현(tower-http)을 쓴다.
  - 목록과 상세 조회는 Dioxus 서버 함수로 만든다. 화면이 서버에서 그려질 때 바로 불러 쓴다.
- **방송 번호 해석**: 주소의 번호는 단축 URL과 같은 규칙으로 읽는다.
  - ASCII 숫자만 받는다.
  - 앞에 0이 붙으면 안 된다.
  - 1 이상이어야 한다.
  - i64 범위 안이어야 한다.

  어긋나면 DB를 보지 않고 "방송을 찾을 수 없습니다"를 보여 준다.
- **등록 흐름**:
  - multipart 필드를 스트리밍으로 읽어 보관 폴더 안의 임시 파일에 바로 쓴다. 메모리에 모으지 않는다.
  - 받는 도중 최대 크기(기본 2 GiB, 설정 가능)를 넘으면 그 즉시 중단하고 413으로 거절한다.
  - 다음을 확인하고 실패하면 400으로 거절한다.
    - 파일 이름 확장자가 `.mp4`(대소문자 무시)인지
    - 파일 앞부분 4~8바이트가 `ftyp`인지

    코덱은 검사하지 않는다(ADR 0001).
  - 제목 규칙을 통과해야 한다.
  - 모든 검사를 통과하면 다음 순서로 저장한다.
    1. 트랜잭션 안에서 방송 정보를 넣어 번호를 받는다.
    2. 임시 파일을 `videos/<번호>.mp4`로 옮긴다.
    3. 커밋한다.
  - 어느 단계에서든 실패하거나 연결이 끊기면 다음과 같이 정리한다.
    - 임시 파일과 옮긴 파일을 지운다.
    - 트랜잭션을 되돌린다.
    - 방송 정보를 남기지 않는다.
- **화면**:
  - 공통:
    - 어두운 배경이다.
    - 맨 위에 "녹화방송" 이름과 "방송 등록" 버튼이 있다.
    - 휴대폰 폭에서도 깨지지 않는다.
  - `/` 목록:
    - 최신순 카드 격자다.
    - 카드에는 회색 썸네일 자리, 제목(길면 말줄임), 등록 시각을 넣는다.
    - 비어 있으면 "아직 방송이 없습니다"와 등록 버튼을 보여 준다.
  - `/broadcasts/{번호}` 상세:
    - 위에 `<video controls playsinline>` 재생기를 두고, 아래에 제목과 등록 시각을 둔다.
    - 목록으로 돌아가는 링크가 있다.
    - 없는 번호면 "방송을 찾을 수 없습니다"와 목록 링크를 404로 보여 준다.
  - `/new` 등록:
    - 제목 입력과 파일 선택(`accept="video/mp4"`)이 있다.
    - 업로드는 `document::eval`로 실행한 작은 JavaScript가 XMLHttpRequest로 보낸다. 진행 이벤트를 Dioxus 쪽으로 보내 진행률을 표시한다.
    - 업로드 중에는 버튼을 막는다.
    - 성공하면 상세 화면으로 이동하고, 실패하면 서버의 한국어 메시지를 보여 준다.
  - 등록 시각은 한국 시간(UTC+9)으로 `YYYY-MM-DD HH:MM` 형식이다.
- **수정·삭제 없음**: 1단계에는 인증이 없으므로 등록과 조회만 제공한다(ADR 0002). 3단계에서 소유자 권한 검사와 함께 추가한다.
- **설정(환경변수)**:
  - `DATABASE_URL`
  - `DATA_DIR`: 영상 보관 폴더. 기본 `./data`
  - `MAX_UPLOAD_BYTES`: 기본 2 GiB
  - `IP`, `PORT`: Dioxus 기본값

  저장소에는 로컬 개발용 예시 값만 담은 `.env.example`을 둔다. 실제 `.env`와 보관 폴더는 git에서 제외한다.
- **README**: 다음을 담는다.
  - 요구 환경: Rust, Dioxus CLI 0.7, Docker
  - 설치와 실행 명령
  - 환경변수 표와 예시
  - 1단계 구현 범위와 범위 밖 항목
  - 직접 확인 절차: 등록 → 목록 → 상세 → 재생과 건너뛰기 → 서버 재시작 → 다시 조회
  - 선택 확인: 같은 와이파이의 휴대폰으로 컴퓨터 주소에 접속해 등록과 재생하기
  - 테스트 실행 방법과 결과
- **제출**: 공개 GitHub 저장소 `haroobuzii/chzzk`에 올린다. 1단계가 끝나면 `step-1` 태그를 붙이고, `tree/step-1` 주소로 제출한다.

## Testing Decisions

- 좋은 테스트는 외부 동작만 검증한다.
  - HTTP 요청을 보내고, 응답과 그 뒤 다시 조회한 결과로 판단한다.
  - 내부 함수 호출, 파일 이름 짓는 방식, SQL 문장은 검증하지 않는다.
- **주 seam: 서버 HTTP 라우터 전체.**
  - 테스트마다 `#[sqlx::test]`로 새 임시 DB를 받고, 빈 임시 보관 폴더를 만든다.
  - 서버를 띄우지 않고, 등록 라우트와 영상 라우트가 붙은 라우터에 요청을 직접 넣는다(`oneshot`).
  - DB와 디스크는 가짜로 바꾸지 않는다.
  - 검증 대상:
    - 유효한 제목과 MP4로 등록하면 201과 번호가 오고, 목록과 단건 조회에 나타난다.
    - 다음 경우는 거절된다. 이때 방송이 생기지 않고 보관 폴더에 파일도 남지 않는다.
      - 제목 위반
      - 파일 없음
      - 확장자가 `.mp4`가 아닌 파일
      - `ftyp` 없는 `.mp4` 파일
      - 크기 초과
    - 업로드 본문이 중간에 끊기면 방송과 파일이 남지 않는다.
    - 목록은 최신 등록순이다.
    - 영상 전송은 이렇게 응답한다.
      - Range 요청에는 206과 정확한 바이트 범위
      - Range 없는 요청에는 200과 전체 파일
    - 없는 번호와 번호가 아닌 값으로 영상을 요청하면 404가 온다.
    - 같은 DB에 새로 연결해도(재시작 시나리오) 방송과 영상이 그대로 조회된다.
- **보조 seam: 제목 규칙 단위 테스트.** 아래 경계를 확인한다.
  - 공백 제거
  - 빈 문자열과 공백만 있는 문자열
  - 100자와 101자
  - 한글과 이모지의 문자 수
- 테스트용 MP4는 `ftyp` 시그니처를 가진 작은 바이트 열이면 충분하다. 코덱을 검사하지 않기 때문이다. 실제 재생 확인에 쓸 작은 샘플 MP4는 README 확인 절차에서 안내한다.
- 선행 사례는 단축 URL 과제(`haroobuzii/short-url`)다.
  - `#[sqlx::test]` DB 테스트
  - 리다이렉트·404 응답 테스트
  - URL 검사 단위 테스트
- 화면 컴포넌트 테스트와 E2E 테스트는 이번 단계에서 하지 않는다. 화면은 README 확인 절차로 직접 확인한다.

## Out of Scope

- 인증과 인가, 방송 소유자 개념 (3단계)
- 방송 수정과 삭제 (3단계)
- 라이브 송출과 시청, 방송 종류 구분 (2단계)
- 댓글 (3단계), 도네이션 (4단계)
- 영상 변환(HLS 등), 화질 선택, 코덱 검사
- 썸네일 생성, 재생 시간 표시
- 목록 페이지네이션, 검색, 정렬 옵션
- 원격 저장소(S3 등) 구현. 영상 보관 모듈 경계만 둔다.
- 실제 서버 배포와 HTTPS
- 업로드 이어 올리기(resumable upload)
- 도배 방지(요청 횟수 제한)

## Further Notes

- 결정 배경은 docs/adr/에 있다.
  - 0001: 원본 MP4 전송
  - 0002: 인증이 없으니 수정·삭제 없음
  - 0003: Dioxus fullstack 크레이트 하나
- 2단계를 내다본 메모:
  - 휴대폰 브라우저 getUserMedia → WebRTC(WHIP) → 미디어 서버 → 시청자(WHEP 또는 HLS) 구조를 예정한다.
  - 휴대폰 카메라에는 HTTPS가 필요하므로 2단계에서 배포 방식을 정한다. 단축 URL처럼 Railway를 쓰면 영상 보관 폴더에 볼륨이 필요하다.
  - 목록에 녹화 방송과 라이브 방송이 함께 나오므로, GLOSSARY.md의 "방송"을 두 종류로 나눠야 한다.
- 인증 없이 공개 인터넷에 올리면 누구나 대용량 파일을 올릴 수 있다. 1단계는 로컬 실행까지만 하므로 범위 밖이다.
