# Spec: 4단계 후원(도네이션)

Status: ready-for-agent

## Problem Statement

3단계까지 시청자는 방송을 보고 댓글을 남길 수 있지만, 마음에 드는 방송자를 응원할 방법은 말뿐이다. 방송자도 누가 자신을 응원했는지 알 수 없다.

이 스펙은 "치지직 만들기" 과제 4단계 중 마지막 단계다. 1~3단계의 기능은 모두 유지하며 확장한다.

- 1단계 녹화 방송: `.scratch/recorded-broadcasts/spec.md`
- 2단계 라이브 방송: `.scratch/live-broadcasts/spec.md`
- 3단계 로그인·소유자·댓글: `.scratch/auth-and-comments/spec.md`

채점은 소스와 README만 읽는 정적 평가다. 특히 세 가지를 본다.

- 서버가 결제 승인과 금액·받는 사람을 확인한 뒤에야 후원을 확정하는가.
- 같은 결제 건이 두 번 확정되지 않는가.
- README에 성공·실패·취소·중복 통지를 확인하는 방법이 있는가.

## Solution

로그인한 사용자가 방송 상세 화면에서 "후원하기"를 누르고, 금액과 짧은 메시지를 골라 토스페이먼츠 **테스트 모드** 결제창으로 결제한다. 실제 돈은 오가지 않는다(ADR 0007).

- **주문서가 먼저**: 서버가 먼저 주문서를 만든다. 주문서에는 주문 번호, 금액, 방송, 받는 사람(방송 소유자), 후원자가 들어간다.
- **승인 확인**: 결제 뒤 돌아오면 서버가 순서대로 확인한다.
  1. 돌아온 금액이 주문서와 같은지
  2. 비밀 키로 토스 승인 API를 부른다
  3. 토스 응답의 상태·금액·주문 번호가 주문서와 같은지

  이 확인을 모두 통과해야 후원이 확정된다.
- **승인 통지**: 토스가 보내는 승인 통지(웹훅)도 받는다. 내용을 믿지 않고 토스에 다시 물어 확인한다. 돌아온 화면과 승인 통지가 몇 번 오든 주문서 하나는 한 번만 확정된다.
- **표시**: 방송 상세 화면에 후원 합계와 내역(후원자, 금액, 메시지, 시각)이 보인다. 결제가 실패하거나 취소되면 그 이유를 보여 주고 후원은 쌓이지 않는다.
- **안전장치**: 서버는 `test_`로 시작하는 토스 키로만 켜진다.

## User Stories

### 후원하기

1. 후원자로서, 방송 상세 화면에서 "후원하기"를 눌러 그 방송의 소유자에게 후원하고 싶다. 좋아하는 방송자를 응원하기 위해서다.
2. 후원자로서, 녹화 방송과 라이브 방송 모두에서 후원하고 싶다.
3. 후원자로서, 1,000원·5,000원·10,000원·50,000원 버튼으로 금액을 빠르게 고르고 싶다.
4. 후원자로서, 금액을 직접 입력하고 싶다. 1,000~500,000원, 100원 단위다.
5. 후원자로서, 금액 규칙에 맞지 않으면 결제창이 열리기 전에 이유를 보고 싶다.
6. 후원자로서, 100자 이하의 응원 메시지를 함께 남기고 싶다. 쓰지 않아도 된다.
7. 후원자로서, 결제창에서 받는 방송자와 금액을 확인하고 싶다.
8. 방문자로서, 로그인하지 않았으면 "후원하기" 대신 "로그인하고 후원하기"를 보고 싶다. 누르면 로그인한 뒤 이 방송으로 돌아온다.
9. 방문자로서, 로그인하지 않고 후원 요청을 직접 보내도 서버가 거절하기를 원한다.
10. 사용자로서, 소유자가 없는 예전 방송에는 후원 버튼이 보이지 않기를 원한다. 서버도 거절한다.
11. 소유자로서, 내 방송에서는 후원 버튼이 보이지 않기를 원한다. 나에게 후원할 수 없고, 서버도 거절한다.
12. 후원자로서, 결제창에서 결제를 마치면 결과 화면에서 "후원이 완료되었습니다"와 방송·금액을 보고 싶다. 결과 화면에는 방송으로 돌아가는 링크가 있다.
13. 후원자로서, 결제가 실패하면 실패 이유를 보고, 후원은 쌓이지 않기를 원한다.
14. 후원자로서, 결제창을 닫아 취소하면 "결제를 취소했습니다"를 보고, 후원은 쌓이지 않기를 원한다.
15. 후원자로서, 결제창을 연 채 오래 두었다가 돌아오면 "시간이 지나 결제가 취소되었어요"를 보고 싶다.
16. 후원자로서, 결과 화면을 새로고침하거나 뒤로 갔다 다시 와도 후원이 두 번 쌓이지 않기를 원한다.

### 서버의 확인

17. 방송자로서, 결과 화면의 "성공" 표시만으로는 후원이 확정되지 않기를 원한다. 서버가 결제 회사에 직접 확인해야 한다.
18. 방송자로서, 누군가 돌아오는 주소의 금액을 바꿔도(예: 100,000원을 1,000원 결제로) 후원이 확정되지 않기를 원한다.
19. 방송자로서, 후원의 받는 사람과 금액이 처음 "후원하기"를 누를 때 서버가 정한 값으로만 기록되기를 원한다.
20. 방송자로서, 결제 회사가 같은 승인 통지를 여러 번 보내도 후원이 한 번만 쌓이기를 원한다.
21. 방송자로서, 돌아온 화면과 승인 통지가 거의 동시에 와도 후원이 한 번만 쌓이기를 원한다.
22. 방송자로서, 꾸며낸 승인 통지(가짜 금액, 없는 결제)로는 후원이 생기지 않기를 원한다.
23. 운영자로서, 결제 회사 승인 요청이 실패한 경우에도 결제 회사에 다시 조회해 실제 상태로 판단하기를 원한다. 승인 실패가 곧 결제 실패는 아니기 때문이다.
24. 운영자로서, 결제 대기로 30분이 지난 주문서가 만료로 정리되기를 원한다.

### 보기

25. 시청자로서, 방송 상세 화면에서 그 방송의 후원 합계(금액과 건수)를 보고 싶다.
26. 시청자로서, 후원 내역을 최신순으로 보고 싶다. 내역에는 후원자 아이디, 금액, 메시지, 시각(한국 시간)이 있다.
27. 시청자로서, 로그인하지 않아도 후원 합계와 내역을 볼 수 있기를 원한다.
28. 시청자로서, 라이브 방송을 보는 동안 후원 내역과 합계가 5초마다 갱신되기를 원한다.
29. 시청자로서, 확정되지 않은 주문서(결제 대기, 실패, 취소, 만료)는 내역과 합계에 보이지 않기를 원한다.

### 안전과 설정

30. 사용자로서, 이 서비스에서 실제 돈이 빠져나가지 않기를 원한다. 서버는 테스트 키로만 켜진다.
31. 운영자로서, 토스 키를 `.env`에만 두고 저장소에는 올리지 않기를 원한다. 비밀 키는 브라우저로 가지 않는다.
32. 운영자로서, 토스 키 없이 서버를 켜도 1~3단계 기능은 그대로 동작하기를 원한다. 후원 화면은 "후원 기능을 쓰려면 토스 테스트 키가 필요해요"를 보여 준다.
33. 운영자로서, `.env`의 설정 하나로 승인을 일부러 실패시켜 실패 화면을 확인하고 싶다(테스트 키일 때만).
34. 운영자로서, 서버를 재시작해도 주문서와 확정된 후원이 그대로 남기를 원한다.

### 1~3단계, 채점자

35. 사용자로서, 1~3단계의 녹화·라이브·로그인·소유자·댓글 기능이 그대로 동작하기를 원한다.
36. 채점자로서, README에서 토스 테스트 키를 받는 방법과 `.env` 예시(자리표시자)를 보고 싶다.
37. 채점자로서, README에서 성공·실패·취소·승인 통지 중복을 확인하는 절차를 보고 싶다. 중복 통지 확인에는 `curl`로 같은 통지를 두 번 보내는 예시가 들어간다.
38. 시청자로서, 후원 칸과 결과 화면에서 "테스트 결제 · 실제로 돈이 나가지 않아요"를 보고 싶다. 실제 돈이 오가는 것으로 오해하지 않기 위해서다.
39. 채점자로서, 4단계 시점의 코드를 `step-4` 태그로 보고 싶다. `step-1`~`step-3`은 그대로 남는다.

## Implementation Decisions

- **용어**: GLOSSARY.md의 후원, 후원자, 주문서, 승인 확인, 승인 통지와 기존 용어(방송, 소유자, 사용자, 로그인)를 쓴다. 받는 사람은 그 방송의 소유자다.
- **결제 서비스**: 토스페이먼츠 **결제창(API 개별 연동) v2 테스트 키**를 쓴다(`test_ck_` 클라이언트 키, `test_sk_` 시크릿 키). 사실 메모는 `docs/toss-payments.md`에 있다.
  - 브라우저: `https://js.tosspayments.com/v2/standard` SDK로 카드 결제창을 연다. `customerKey`는 익명 고객이다.
  - 서버의 토스 API
    - 승인: `POST /v1/payments/confirm`
    - 조회: `GET /v1/payments/{paymentKey}`, `GET /v1/payments/orders/{orderId}`

    Basic 인증(`시크릿키:`)으로 부르고, 승인에는 `Idempotency-Key`(주문 번호)를 붙인다.
- **스키마**: 날짜·시각 이름의 마이그레이션으로 주문서 표를 만든다.
  - 칸
    - 주문서 번호(identity)
    - 주문 번호(토스 `orderId`): 서버가 만든 추측 불가능한 무작위 값, 6~64자 `[A-Za-z0-9_-]`, 고유
    - 방송 번호
    - 후원자, 받는 사람
    - 금액(정수 원): `CHECK` 1,000~500,000이고 100으로 나누어떨어진다
    - 메시지: 비어 있을 수 있고, 100자 `CHECK`
    - 상태(결제 대기·확정·실패·취소·만료)
    - 토스 결제 키(`paymentKey`): 고유, 확정되면 반드시 있다
    - 실패 코드·메시지
    - 만든 시각, 확정 시각
  - **방송이 지워져도 주문서는 남긴다**(방송 번호는 비운다). 돈과 관련된 기록이라 방송과 함께 지우지 않는다. 지워진 방송의 후원은 어디에도 표시되지 않는다.
  - `UNIQUE(payment_key)`와 주문 번호 고유 제약이 "결제 한 건 = 후원 한 건"을 DB에서 보장한다.
- **상태 바꾸기**: 상태는 "결제 대기일 때만"을 조건으로 하는 UPDATE 하나로 바꾼다. 그래서 동시에 온 확인 요청 중 하나만 이기고, 확정·실패·취소·만료는 되돌아가지 않는다.
- **모듈**:
  - **후원 규칙**: 금액(범위, 100원 단위)과 메시지(앞뒤 공백 제거, 100자) 순수 함수.
  - **주문서 저장소**: 만들기, 주문 번호로 찾기, 조건부 전환(확정, 실패, 취소, 만료), 방송별 확정 후원 목록·합계.
  - **결제 연결(토스)**: 결제 회사와 주고받는 코드는 모두 이 모듈 하나에 둔다(ADR 0007). 나머지 모듈은 "이 주문 번호·금액으로 승인됐다/아니다"라는 결과 타입만 다룬다. 설정된 토스 API 주소(기본 `https://api.tosspayments.com`, 테스트가 가짜 서버로 바꾼다)로 승인·조회를 부른다.
    - 응답은 상태, 금액, 주문 번호, 결제 키만 읽는다.
    - `TOSS_TEST_FAIL_CODE`가 있으면 승인 요청에 `TossPayments-Test-Code` 헤더를 붙인다.
  - **승인 확인**: 돌아온 화면과 승인 통지가 함께 쓰는 한 함수다. 순서는 아래와 같다.
    1. 주문서가 결제 대기인지 본다. 이미 확정이면 그 결과를 그대로 돌려준다(멱등). 이미 실패·취소·만료면 그대로다.
    2. 30분이 지났으면 만료로 바꾼다.
    3. 금액이 주문서와 다르면 토스를 부르지 않고 실패(`amount_mismatch`)로 바꾼다.
    4. 토스 승인을 부른다. 응답 상태가 `DONE`이고 금액·주문 번호가 같을 때만 확정한다.
    5. 승인 요청이 오류(이미 처리됨 등)를 돌려주면 주문 번호로 토스를 다시 조회해 실제 상태로 판단한다.
  - **만료 정리**: 1분마다 결제 대기로 30분이 지난 주문서를 만료로 바꾼다. "지금 시각"을 받는 함수로 두어 테스트가 시간을 흉내 낸다.
  - **화면**: 후원 칸(상세 화면), 결과 화면(`/donations/success`, `/donations/fail`).
- **HTTP 계약**: 직접 덧붙인 axum 라우트다. 실패 응답은 기존 `{code, message}`, 401/403 규칙은 3단계와 같다.
  - `POST /api/broadcasts/{번호}/donations` `{amount, message?}`
    - 로그인이 필요하다(401).
    - 거절: 없는 방송은 404, 소유자 없는 방송은 400(`no_owner`), 내 방송은 400(`own_broadcast`), 금액·메시지 위반은 400, 토스 키가 없으면 503(`donations_disabled`).
    - 성공하면 201과 `{order_id, amount, order_name, client_key}`를 준다. 클라이언트 키는 원래 공개해도 되는 키다.
  - `POST /api/donations/confirm` `{payment_key, order_id, amount}`
    - 돌아온 결과 화면이 부른다. 로그인은 요구하지 않는다(세션이 끊겨도 결제는 확정되어야 한다).
    - 응답은 `{status, broadcast_id, amount}` 또는 실패 이유다. 같은 요청을 다시 보내도 같은 결과다.
  - `POST /api/donations/fail` `{order_id?, code, message}`
    - 결과 화면(실패·취소)이 부른다. 로그인한 후원자 본인의 결제 대기 주문서만 바꾼다.
    - 바꾸는 상태: 토스 취소 코드(`PAY_PROCESS_CANCELED`, `USER_CANCEL`)면 취소, 그 밖은 실패.
    - 주문 번호가 없거나 남의 주문서면 아무것도 바꾸지 않고 204를 준다.
  - `POST /api/payments/toss-webhook`: 토스 승인 통지.
    - 본문에서 결제 키만 읽고, 토스 조회 API로 실제 결제를 다시 가져와 승인 확인 함수로 넘긴다.
    - 조회한 상태에 따라 바꾼다. `DONE`이면서 금액·주문 번호가 맞으면 확정, `CANCELED`·`ABORTED`·`EXPIRED`면 결제 대기 주문서를 실패·취소·만료로 바꾼다.
    - 언제나 빠르게 200을 준다. 모르는 주문서나 위조도 200으로 받고 무시한다.
    - 쿠키도 `Origin`도 없는 서버 간 요청이라 CSRF 확인을 통과한다.
  - `GET /api/broadcasts/{번호}/donations`: 누구나. `{total_amount, count, items: [{donor, amount, message, confirmed_at}]}`, 확정된 후원만 최신순이다.
- **설정(환경변수)**:
  - `TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`
    - 둘 다 없으면 후원 기능이 꺼진 채로 켜진다.
    - 하나만 있거나 `test_`로 시작하지 않으면 서버가 켜지지 않고 이유를 알려 준다.
  - `TOSS_API_URL`: 기본 `https://api.tosspayments.com`
  - `TOSS_TEST_FAIL_CODE`: 비어 있으면 끔. 예: `REJECT_CARD_PAYMENT`
  - `.env.example`에는 자리표시자만 둔다(`test_ck_여기에_내_테스트_클라이언트_키` 같은 값).
- **화면**:
  - **테스트 결제 표시**: 후원 칸과 결과 화면에 언제나 "테스트 결제 · 실제로 돈이 나가지 않아요"를 보여 준다. 나중에 배포했을 때 보는 사람이 헷갈리지 않게 하기 위해서다.
  - **결제 수단**: 카드 결제창 하나를 연다(`method: CARD`). 그 창 안에서 카드와 간편결제(토스페이·네이버페이 등)를 고를 수 있다. 계좌이체·휴대폰 버튼은 두지 않는다.
  - **후원 칸**: 방송 상세 화면(녹화·라이브) 안에 둔다.
    - 합계("총 35,000원 · 7건")와 내역을 보여 준다.
    - 다른 사람의 방송이면 금액 버튼 넷과 직접 입력, 메시지 입력, "후원하기"를 둔다. 로그인 전에는 "로그인하고 후원하기"를 둔다. 소유자 없는 방송·내 방송에는 후원 입력이 없다.
    - 라이브 방송 중이면 5초마다 다시 불러온다.
  - **결제 흐름**: "후원하기"를 누르면 주문서 API를 부르고, `document::eval`로 토스 SDK를 불러와 `requestPayment`를 부른다. 돌아올 주소는 `window.location.origin`에 아래 경로를 붙여 만든다.
    - `successUrl`: `/donations/success`
    - `failUrl`: `/donations/fail`
  - **결과 화면**
    - `/donations/success`는 주소의 `paymentKey`·`orderId`·`amount`로 확인 API를 부르고 결과를 보여 준다. 화면은 서버 응답만 믿는다.
    - `/donations/fail`은 `code`·`message`·`orderId`로 실패 API를 부르고 실패 또는 취소 안내를 보여 준다.
    - 둘 다 방송으로 돌아가는 링크가 있다.
- **README**: 1~3단계 내용을 유지하고 아래를 더한다.
  - 4단계 범위와 범위 밖
  - 토스 개발자센터에서 테스트 키 받는 법과 `.env` 예시
  - 테스트 모드라 돈이 나가지 않는다는 안내, 테스트 키 강제
  - 확인 절차
    - **성공**: 결제창에서 카드 정보를 넣고 결제한다.
    - **실패**: `TOSS_TEST_FAIL_CODE`를 넣고 다시 켠 뒤 결제한다.
    - **취소**: 결제창을 닫는다.
    - **금액 조작 거절**: 돌아온 주소의 `amount`를 바꿔 연다.

## Testing Decisions

- 좋은 테스트는 외부 동작만 검증한다. 우리 서버에 HTTP 요청을 넣고 응답과 그 뒤의 조회 결과(합계, 내역, 주문서 상태)로 판단한다. SQL과 내부 호출 순서는 검증하지 않는다.
- **주 seam: 서버 HTTP 라우터 전체**(1~3단계와 같다). `#[sqlx::test]` 임시 DB, 3단계의 손님(비로그인, A, B)을 쓴다.
  - **가짜 토스 서버**: 임의 포트에 띄운 작은 axum 서버다.
    - 받은 승인·조회 요청(헤더 포함)을 기록한다.
    - 테스트가 정한 대답을 돌려준다(`DONE`, 다른 금액, 카드 거절 오류, 이미 처리됨, 조회 결과).
    - 2단계 가짜 MediaMTX와 같은 방식이다.
  - 만료 정리는 "한 번 정리" 함수를 테스트가 지금 시각을 넘겨 부른다.
- **검증 대상**
  - **주문서 만들기**
    - 비로그인은 401이다.
    - 소유자 없는 방송, 내 방송, 금액 위반(999, 500,100, 1,050), 101자 메시지는 400이다.
    - 없는 방송은 404, 키가 없으면 503이다.
    - 성공하면 201이고, 결제 대기라 합계·내역에는 없다.
  - **승인 확인**
    - 토스가 `DONE`과 같은 금액·주문 번호로 답하면 확정되고 합계·내역에 나타난다. 받는 사람은 방송 소유자, 금액은 주문서 금액이다.
    - 돌아온 금액이 다르면 토스에 승인 요청이 가지 않고 실패가 된다.
    - 토스 응답 금액이 다르거나 `DONE`이 아니면 확정되지 않는다.
    - 토스가 거절 오류를 주면 다시 조회한 뒤 실패가 된다.
    - "이미 처리됨" 오류에 조회 결과가 `DONE`이면 확정된다.
    - 같은 확인 요청을 두 번 보내도 한 번만 확정되고, 두 번째도 같은 결과를 돌려준다.
    - 30분이 지난 주문서는 만료가 되고 확정되지 않는다.
    - `TOSS_TEST_FAIL_CODE`가 있으면 승인 요청에 테스트 헤더가 붙는다.
  - **실패·취소**
    - 후원자 본인이 실패 API를 부르면 취소 코드는 취소, 다른 코드는 실패가 된다.
    - 다른 사용자나 비로그인이면 바뀌지 않는다.
  - **승인 통지**
    - 통지를 두 번 보내도 한 번만 확정된다.
    - 통지가 먼저 오고 확인 요청이 나중에 와도(또는 반대로) 한 번만 확정된다.
    - 본문의 금액을 부풀린 통지도 토스 조회 결과로만 판단한다.
    - 모르는 결제 키는 200이고 아무것도 생기지 않는다.
  - **목록·합계**: 확정된 것만, 최신순, 합계와 건수가 맞다. 누구나 조회할 수 있다.
  - **방송 삭제**: 방송을 지워도 주문서는 남고, 그 방송의 후원 조회는 404다.
  - **설정**: `test_`가 아닌 키, 한쪽만 있는 키는 설정 읽기에서 거절된다. 둘 다 없으면 후원이 꺼진다.
  - **재시작**: 같은 DB에 새로 연결해도 확정된 후원이 그대로다.
- **보조**: 금액·메시지 규칙 단위 테스트(경계값), 주문 번호 생성(형식, 서로 다름).
- **1~3단계 테스트 151개**는 수정 없이 통과해야 한다(CODING_STANDARDS.md의 예외 규칙은 그대로).
- 선행 사례: 가짜 MediaMTX(`src/live/fake_mediamtx.rs`), 3단계 손님(`src/auth/personas.rs`), 상태 감시기의 "한 번 맞추기".
- 진짜 토스 결제창에서 카드 정보를 넣는 확인은 사람이 한다(README 절차). 구현 중에는 받은 테스트 키로 승인·조회 API의 실제 응답 모양만 확인할 수 있다.

## Out of Scope

- 실제 결제(라이브 키), 사업자 등록·계약
- 환불(결제 취소 API), 부분 취소
- 정산, 방송자 수익 화면, 출금
- 후원 순위, 후원 알림 팝업·음성, 후원 목표
- 카드 결제창 밖의 결제 수단(계좌이체, 휴대폰, 가상계좌) 버튼. 계좌이체는 테스트에도 공동인증서가 필요하고, 가상계좌는 입금 대기 상태가 따로 생긴다. 결제 연결 경계(ADR 0007) 덕분에 나중에 더할 수 있다.
- 결제위젯(주문서형). 전자결제 계약 뒤에 받는 키가 필요하다.
- 웹훅 서명 검증. 통지 내용을 쓰지 않고 토스에 다시 조회하므로 필요 없다.
- 실제 서버 배포

## Further Notes

- 결정 배경: ADR 0007(토스 테스트 모드, 주문서, 승인 확인, 중복 방지, 테스트 장치). 토스 사실 메모: `docs/toss-payments.md`.
- 토스 테스트 환경은 API마다 분당 100건으로 제한된다. 자동 테스트는 가짜 토스 서버를 쓰므로 영향이 없다.
- 토스는 승인 통지를 10초 안에 200을 받지 못하면 최대 7번 다시 보낸다. 그래서 통지 처리는 빠르게 200을 돌려준다.
- 이 단계에서 돈과 관련된 기록(주문서)은 방송이 지워져도 남긴다. 이전 단계에서 방송과 함께 지워지던 댓글과 다르게 다룬다.
